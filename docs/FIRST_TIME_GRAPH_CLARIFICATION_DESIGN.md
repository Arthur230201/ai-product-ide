# 首次建图必须澄清项设计（专家联合分析）

> 目标：用户第一次生成图节点时，由 AI 完成澄清追问。除「移动端 / PC 端」外，还有哪些信息是**必须**的？

---

## 一、多角色共识：必须澄清的维度

### 1. 视口 / 端类型（移动 vs 桌面）—— **必须**

| 角色 | 理由 |
|------|------|
| **产品** | 决定信息架构与页面粒度：移动端多为单任务、少层级；PC 端可多栏、多 Tab、复杂表单。 |
| **UX** | 布局与交互范式完全不同（触控 vs 键鼠、单列 vs 多列、底部导航 vs 侧边栏）。 |
| **技术** | 视口驱动后续 UI 生成与视口锁定（375 vs 1280）、组件与布局约束不同。 |

**结论**：已明确要求，必选其一（移动 / 桌面），可扩展为「移动 / 平板 / 桌面」若产品需要。

---

### 2. 业务对象与核心场景—— **必须**

| 角色 | 理由 |
|------|------|
| **产品** | 不同业务对象（人/物/流程/内容/资金）对应不同页面类型与流程（CRM vs 库存 vs 审批 vs 内容库）。 |
| **领域** | 避免「企业管理系统」这种泛描述，收敛到可执行的场景（如：销售跟进、仓储入库、报销审批）。 |

**结论**：当前澄清已包含「3–4 个业务场景选项」，本质是在补足「业务对象 + 核心场景」。必须保留并优先展示，与视口并列。

---

### 3. 主用户角色与使用场景—— **强烈建议**

| 角色 | 理由 |
|------|------|
| **产品** | 谁用、在什么情境下用（发起人/审批人/外勤/后台）决定页面集合与流程走向。 |
| **UX** | 角色决定信息优先级与操作主路径（如审批人更关注待办与操作区）。 |

**结论**：不必单独一屏追问，可合并到「业务场景」选项中（每个选项内含典型角色与场景），或作为 1 个简短追问（如「主要使用者是？」可选：内部员工 / 客户 / 管理员 / 多角色）。

---

### 4. 范围边界（MVP vs 全量）—— **建议**

| 角色 | 理由 |
|------|------|
| **产品** | 先做核心 3–5 页还是完整站点，直接影响节点数量与复杂度。 |
| **技术** | 避免一次生成过多节点导致性能与可维护性问题。 |

**结论**：可作为可选追问（「先做核心流程还是完整应用？」），或由 AI 根据描述自动推断并在澄清文案中说明（如「将先生成核心 5 页，您可后续再补充」）。

---

### 5. 关键流程/步骤是否明确—— **视情况**

| 角色 | 理由 |
|------|------|
| **产品** | 有明确流程（如：提交 → 审批 → 归档）时，图结构更准确。 |
| **领域** | 流程不清时，可依赖「业务场景」选项补足典型流程。 |

**结论**：不单独作为必选追问；若用户输入中完全无流程信息，可在澄清选项中用「典型流程」描述补足。

---

## 二、必须项汇总（实现优先级）

| 优先级 | 维度 | 说明 | 实现建议 |
|--------|------|------|----------|
| **P0** | 视口类型 | 移动 / PC（必选） | 澄清请求中**显式增加**「请选择使用设备」：选项为「移动端」「桌面端」（可后续加「平板」）。 |
| **P0** | 业务场景 | 用户要做的具体业务类型 | 保留并强化现有「3–4 个业务场景选项」，与视口一起作为首轮澄清的**必选动作**。 |
| **P1** | 主用户角色 | 谁在用 | 可嵌入业务场景选项的 `desc`/`example` 中，或增加 1 个单选（内部/客户/管理员/多角色）。 |
| **P2** | 范围（MVP/全量） | 先做多少 | 可选追问，或由 AI 在澄清文案中给出默认并说明。 |

---

## 三、交互与数据结构建议

1. **首轮澄清统一包含**  
   - 一段简短说明（当前仍可沿用「输入较模糊，请补充」类表述）。  
   - **视口选择**：固定两道选项——「移动端」「桌面端」（前端可渲染为单选或高亮选择）。  
   - **业务场景选择**：保留现有 3–4 个 `options`，用户至少选一个（或选「其他，我会在下一步说明」）。

2. **用户回复结构**  
   - 建议将澄清回复拼成结构化片段，例如：`视口：移动端；场景：库存与资产管理；补充：…`，再与 `initialPrompt` 一起作为 `enrichedPrompt` 传入 `generateGraph`，便于模型与后续 UI 生成使用。

3. **首次建图与「非首次」**  
   - **首次建图**（当前画布无节点或为空白项目）：**始终走澄清流程**（先问视口 + 业务场景，再生成图）。  
   - **非首次**（已有节点）：可按现有逻辑，仅当输入模糊时再澄清，避免重复问视口。

---

## 四、与现有实现的关系

- **现有**：`analyzeInputClarity` → 若 `isVague && confidence < 60` → `generateClarificationRequest` 返回 3–4 个业务场景选项；**未包含视口**。  
- **改动方向**：  
  1. 在澄清请求的 Schema 与 prompt 中**增加视口（viewport）**：选项 `mobile` / `desktop`，并在前端展示为「移动端 / 桌面端」。  
  2. 首次建图时（可由前端传入 `isFirstTimeCreate: true` 或根据 `nodes.length === 0` 判断），**强制先澄清**（视口 + 业务场景），再调用 `generateGraph`。  
  3. 将用户选择的视口与场景写入澄清回复，并在 `enrichedPrompt` 中显式包含（如 `视口：桌面端；业务场景：…；用户补充：…`），以便图生成与后续 UI 生成使用同一视口假设。

以上为「最强大脑 + 专家团队」对「除移动/PC 外还有哪些必须信息」的结论与实现建议；**必须项**为：**视口类型** + **业务场景**；其余为主用户角色（建议）、范围（可选）等。
