# AI 对话框「对话区」方案设计

> 产品方案：为画布底部 AI 对话框增加「对话区」，使用户能像与助手对话一样看到自己的输入与 AI 的回复。

---

## 一、背景与现状

### 1.1 当前形态

- **入口**：画布底部固定条（CommandBar），非编辑模式下居中显示；进入节点详情后，CommandBar 位于预览区底部。
- **交互**：单行/多行输入框 + 附件 + 发送；无历史消息展示。
- **反馈**：AI 执行结果通过 **Toast** 反馈（成功/失败/进度提示），例如「正在按【移动】视口生成…」「UI 代码已更新」「操作失败」等；**没有持久化的对话记录**。
- **能力**：支持两种主流程——**建图/生成节点**（无选中节点）与**编辑当前节点**（选中节点时生成/更新 UI、分析代码等）。

### 1.2 用户诉求

- 希望有一个「和你一样的对话部分」，即：**能看到自己发出去的内容 + AI 的回复**，形成对话流，而不是仅依赖 Toast 一闪而过。
- 目标体验接近常见 AI 聊天产品：**用户消息 + 助手回复** 成对展示，可回溯上下文。

---

## 二、产品目标与原则

### 2.1 产品目标

| 目标 | 说明 |
|------|------|
| **可读性** | 用户发送的内容与 AI 的回复在对话框内持久可见，无需依赖 Toast 或控制台。 |
| **上下文感** | 对话区按时间顺序展示多轮「用户 → AI」，便于理解当前会话在做什么、AI 说了什么。 |
| **与现有流程兼容** | 不改变现有「输入 → 调用 generateGraph / generateUIFromText / 更新节点」等逻辑，仅在 UI 层增加展示与必要的数据结构。 |

### 2.2 设计原则

- **对话区服务于「展示」**：以展示用户输入与 AI 文本回复为主；若某次调用无文本回复（仅更新画布/节点），可展示简短状态摘要（如「已生成 3 个节点并完成布局」）。
- **不替代 Toast**：关键结果（成功/失败/错误详情）仍可保留 Toast，对话区作为**主信息区**，Toast 作为**即时提醒**。
- **复杂度可控**：首版不引入多轮对话上下文再发给后端（即不改变现有单轮请求语义），仅在前端展示「用户消息 + 本轮 AI 回复」。

## 三、用户故事与场景

| 角色 | 故事 | 验收 |
|------|------|------|
| 产品/设计 | 作为画布使用者，我希望在底部 AI 对话框里看到我刚刚输入的内容，以便确认没有输错或漏发。 | 发送后，输入内容作为「用户消息」出现在对话区。 |
| 产品/设计 | 作为画布使用者，我希望在对话框里看到 AI 的回复内容（文字说明、结果摘要等），而不是只有 Toast，以便事后回顾和截图。 | AI 返回的文本/摘要作为「助手消息」出现在对话区。 |
| 产品/设计 | 作为画布使用者，我希望对话区与输入框同时存在，上面是历史对话，下面是输入，类似常见聊天界面。 | 布局为：上为可滚动对话列表，下为固定输入区。 |

## 四、布局放在哪里

### 4.1 挂载点与占位原则（不悬浮、不遮盖）

CommandBar 使用**占位布局**：始终在文档流中占据一块区域，**不**使用 `position: fixed/absolute` 悬浮在内容之上，避免遮盖画布或预览区。

| 场景 | 挂载位置 | 当前实现 |
|------|----------|----------|
| **画布模式**（未打开节点详情） | 页面底部 | `InfiniteCanvas.tsx`：根容器 `flex flex-col`，上方画布区 `flex-1 min-h-0`，CommandBar 容器 `flex-shrink-0` 在底部，`max-w-[48rem]` 居中。 |
| **节点详情模式**（已打开某节点） | 右侧栏底部、预览区下方 | `NodeDetailPanel.tsx`：右侧列 `flex flex-col`，预览区 `flex-1 min-h-0`，CommandBar 容器 `flex-shrink-0`，`max-w-[42rem]`。 |

即：画布/预览区在上方占满剩余空间，CommandBar 在下方占位，**不遮盖**上方内容。

### 4.2 CommandBar 内部布局（新增对话区）

在 **CommandBar 组件内部**，由「单一块输入区」改为 **纵向两段**：

```
┌─────────────────────────────────────────────────────────┐
│  对话区（新增）                                           │
│  ┌─────────────────────────────────────────────────────┐ │
│  │  [用户] 帮我生成一个登录页                            │ │
│  │  [AI]   已为「登录」生成并更新 UI 代码。              │ │
│  │  [用户] 改成移动端风格                               │ │
│  │  [AI]   正在按【移动】视口生成…                      │ │
│  └─────────────────────────────────────────────────────┘ │
│  最大高度 240～280px，超出内部滚动，新消息在底部          │
├─────────────────────────────────────────────────────────┤
│  输入区（现有）                                           │
│  [附件] [输入框………………………………] [发送]                   │
│  进度条 / 编辑中提示 等                                   │
└─────────────────────────────────────────────────────────┘
```

- **上段**：对话区（可滚动），仅在本组件内通过 flex 或 grid 与下段分隔。
- **下段**：现有表单（输入框、附件、发送、进度条、编辑中提示等）整体下移，视觉上「贴底」或保留少量 bottom 间距。

两处场景下 CommandBar 的**宽度**仍由各自父容器控制（画布模式 48rem、详情模式 42rem），对话区与输入区共享该宽度，无需单独指定。

### 4.3 整体高度与滚动

- **对话区**：设 `max-height: 240px`（或 280px），`overflow-y: auto`，内部滚动；无消息时高度可收缩（如 0 或最小 40px 占位）。
- **CommandBar 整体**：画布模式已有限高 `maxHeight: calc(100vh - 4rem)`，详情模式在右侧栏内由 flex 分配，一般无需再设整体 max-height；若需可加 `max-h-[50vh]` 防止在窄屏下占满屏。

## 五、方案设计（逻辑与数据）

### 5.1 整体形态（与布局对应）

- **形态**：CommandBar 由「仅输入条」改为「上对话区 + 下输入区」。
  - **对话区**：可滚动列表，每条为「用户消息」或「助手消息」气泡/卡片；新消息在底部，自动滚动到底。
  - **输入区**：保持现有输入框、附件、发送、进度条等；可保留聚焦展开、拖拽上传等行为。

### 5.2 消息类型与内容

| 类型 | 触发时机 | 展示内容建议 |
|------|----------|----------------------|
| **用户消息** | 用户点击发送时 | 当前输入框文本 + 若有附件，可展示「附：1 个文件」或文件名列表；支持纯文本 + 简短附件摘要。 |
| **助手消息** | 服务端返回后 | 优先展示**后端返回的文本内容**（若 API 有返回 message / summary / reasoning 等）；若无，则用**前端生成的摘要**，例如：「已根据描述生成画布并添加 3 个节点」「已为「首页」更新 UI 代码」「生成失败：超时」等。 |
| **助手消息（进行中）** | 请求发出后、返回前 | 占位条，如「正在生成画布…」「正在生成 UI…」，可配合现有 progress/loadingStep；返回后替换为最终助手消息。 |

### 5.3 数据模型（前端）

- **消息列表**：`messages: Array<{ id: string; role: 'user' | 'assistant'; content: string; timestamp?: number; status?: 'sending' | 'done' | 'error'; attachmentSummary?: string }>`
  - `content`：用户消息为输入文本；助手消息为 AI 文本回复或前端摘要。
  - `status`：可选，用于区分「发送中」「完成」「失败」的样式（如 loading 图标、错误样式）。
  - `attachmentSummary`：可选，用户消息若有附件，可存「附：2 个文件」等。
- **作用域**：首版建议**会话级**——即当前页面/画布会话内累积，刷新或关闭后清空；不要求持久化到服务端或本地存储（后续可加）。

### 5.4 与现有逻辑的衔接

- **发送时**：在现有 `handleSubmit` 中，在发起请求**前**向 `messages` 追加一条 `role: 'user'` 的消息（内容为当前 prompt + 可选 attachmentSummary）；并可选追加一条 `role: 'assistant'`、`status: 'sending'` 的占位消息。
- **请求返回后**：  
  - 若有占位助手消息，则更新该条为 `content`（后端返回文本或前端摘要）、`status: 'done'` 或 `'error'`。  
  - 若后端无文本字段，则前端根据结果类型生成简短摘要（如「已添加 N 个节点」「已更新当前节点 UI」），写入该助手消息的 `content`。
- **Toast**：可保留成功/失败 Toast，与对话区并存；错误详情可同时写入助手消息的 `content`，便于在对话区查看。

### 5.5 与 UI/UX 的对应

- 发送时追加用户消息、返回后更新助手消息；Toast 保留；详见下文「六、UI 与 UX 设计」。

## 六、UI 与 UX 设计

### 6.1 组件结构（CommandBar 内部）

- **外层**：保持现有圆角、边框、背景（如 `bg-zinc-900/95 backdrop-blur-xl border rounded-xl`），整体为一块卡片。
- **内部**：自上而下为两个区块：
  1. **对话区容器**：`flex-shrink-0` 或固定 max-height，内部为可滚动列表。
  2. **输入区容器**：现有 form + 进度条 + 编辑中提示，`flex-shrink-0`，保证始终可见。

### 6.2 对话区

- **容器**：`max-h-[240px]` 或 `max-h-[280px]`，`overflow-y-auto`，`overscroll-behavior: contain`，背景可与卡片一致或略深（如 `bg-zinc-900/50`）。上下留内边距（如 `py-3 px-4`），与输入区有分隔线或间距（如 `border-b border-zinc-800`）。
- **列表**：垂直排列，每条消息一个块；新消息在底部，列表底部留一小段空白便于阅读。

### 6.3 单条消息的视觉规范

| 元素 | 用户消息 | 助手消息 |
|------|----------|----------|
| **对齐** | 靠右（或靠左统一左对齐，用背景区分） | 靠左 |
| **气泡/卡片** | 背景 `bg-cyan-500/20` 或 `bg-cyan-600/30`，边框 `border border-cyan-500/30`，圆角 `rounded-lg`（右侧略尖或统一圆角） | 背景 `bg-zinc-800`，边框 `border border-zinc-700`，圆角 `rounded-lg`（左侧略尖或统一） |
| **文案** | `text-zinc-100`，`text-sm`，可 `max-w-[85%]` 避免过长一行 | `text-zinc-300`，`text-sm`，同宽约束 |
| **身份** | 可选在气泡外标注「你」或图标（人形） | 可选在气泡外标注「AI」或图标（Bot/Sparkles） |
| **附件摘要** | 用户消息若有附件，在正文下方一行小字 `text-zinc-500 text-xs`：「附：1 个文件」或简短文件名 | — |
| **状态** | — | 进行中：气泡内 loading 图标 + 文案「正在生成画布…」；错误：`text-red-400` 或边框 `border-red-500/50` |

建议：用户与助手在**同一垂直流**内交替出现（用户右、助手左），或统一左对齐、仅用背景色和图标区分，避免复杂左右分栏以节省横向空间。

### 6.4 空状态

- 无消息时：对话区可显示占位文案，如「在这里会显示你的输入与 AI 的回复」，`text-zinc-500 text-sm`，居中或左对齐；或留空、仅保留最小高度（如 40px），由输入区撑起视觉重心。

### 6.5 滚动与自动滚底

- 对话区内部滚动，不带动整页。
- 每次追加或更新消息后，将滚动位置设为 `scrollTop = scrollHeight`，使最新消息在视区底部；若用户已向上翻阅历史，可考虑「是否在底部」判断，仅在接近底部时自动滚底，避免打断阅读（MVP 可简化为始终滚底）。

### 6.6 响应式与高度

- **宽度**：与 CommandBar 一致，由父级控制；消息气泡 `max-w-[85%]` 或类似，避免在窄屏下溢出。
- **高度**：对话区 max-height 在 240～280px 间；小屏（如 768px 以下）可略减（如 200px），保证输入区始终可见。

### 6.7 动效（可选）

- 新消息出现：轻量 `opacity` + `transform` 动画（如 0.95 → 1，translateY(4px) → 0），时长 150～200ms。
- 助手「进行中」→「完成」：可替换文案 + 短 fade，避免整块闪烁。

### 6.8 无障碍

- 对话区容器：`role="log"` 或 `aria-live="polite"`，便于读屏将新消息视为追加日志。
- 单条消息：无需单独 role，保持语义化（如 `<p>` 或 `<div>` 内文本）。
- 发送中：对「进行中」的助手消息可加 `aria-busy="true"`。

## 七、后端配合（可选）

- 若现有 API（如 `generateGraph`、`generateUIFromText`）**已有**返回文本字段（如 `message`、`summary`、`reasoning`），前端直接使用即可。
- 若**没有**，首版可仅用前端摘要填充助手消息；后续若希望展示更丰富的 AI 说明，可由后端在响应中增加字段，前端再对接。

## 八、范围与阶段

| 阶段 | 范围 | 说明 |
|------|------|------|
| **MVP** | 对话区布局 + 用户消息 + 助手消息（前端摘要） | 实现上对话区、下输入区；发送时写入用户消息；返回后写入助手消息（内容以前端摘要为主）。 |
| **增强** | 助手消息使用后端返回文本 | 若/当 API 提供可展示文本，替换为 API 内容。 |
| **可选** | 对话持久化、多轮上下文上报 | 按需再做；不影响首版方案。 |

## 九、风险与开放点

- **性能**：消息条数过多时，可限制只保留最近 N 条（如 50），或仅保留当前会话不持久化，避免内存与渲染压力。
- **多请求**：若用户快速连续发送，需明确策略——是排队、禁用发送，还是允许多条「进行中」助手消息；建议首版单条进行中，发送中禁用发送（与现有 loading 一致）。
- **错误展示**：网络错误、超时等，除 Toast 外，在对应助手消息中展示错误文案，便于用户在对话区直接看到。

---

## 十、验收标准（MVP）

1. 打开画布底部 AI 对话框，可见**上方对话区**（可为空或带占位文案）与**下方输入区**（与现有一致）。
2. 用户输入并发送后，**用户消息**出现在对话区，内容为发送的文本（及附件摘要若有）。
3. 请求进行中时，对话区出现**助手「进行中」**状态；请求结束后，该条更新为**助手回复**（文本或前端摘要）。
4. 多轮发送后，对话区按时间顺序展示多对「用户 → 助手」，可滚动查看，新消息在底部并自动滚到底。
