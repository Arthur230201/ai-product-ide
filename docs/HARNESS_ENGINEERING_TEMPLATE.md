# Harness Engineering 可复用模板

> 来源：[OpenAI — 運用工程技術：在智慧體優先的世界中善用 Codex](https://openai.com/zh-Hans-CN/index/harness-engineering/)  
> 本文档为**固定模板**，可复制到任意新项目，按「使用步骤」裁剪后即可让智能体与团队按同一套方法协作。

---

## 一、核心思想

将**脚手架、反馈循环、文档与架构约束**编码为机器可读产物，智能体据此执行代码生成、测试与可观测性任务；工程师侧重**设计环境、明确意图、提供结构化反馈**，而非逐行写代码。

---

## 二、固定结构（新项目必做）

### 1. AGENTS.md（目录表，≤100 行）

- **位置**：仓库根目录 `AGENTS.md`。
- **内容**：项目目标、必读规范（含 ARCHITECTURE 等）、文档索引（指向 `docs/`）、架构边界、与智能体的工作流约定。
- **禁止**：在 AGENTS.md 里写长篇说明；详细内容一律放在 `docs/`。

### 2. docs/ 结构化知识库

| 子目录/文件建议 | 用途 |
|----------------|------|
| `docs/architecture/` 或 `ARCHITECTURE.md` | 架构图、依赖层级、模块边界 |
| `docs/design/` | 设计文档、PRD、产品规范 |
| `docs/plans/` | 执行计划、里程碑、任务分解 |
| `docs/references/` | 外部规范、API、设计系统链接 |

- 用**交叉链接**串联设计与架构文档。
- 可选：CI 或脚本校验文档新鲜度与链接有效性。

### 3. 架构约束（依赖层级）

- 约定**单向依赖**，例如：  
  **Types → Config → Repo → Service → Runtime → UI**
- 用 **Lint/结构测试** 在 CI 中禁止逆向依赖与越层引用。
- 智能体写代码时遵守该层级。

### 4. 工程师角色分工

| 角色 | 由谁做 | 内容 |
|------|--------|------|
| **委托** | 智能体 | 可行性分析、样板代码、初始实现、重复任务 |
| **审查** | 人 | 设计选择、性能、安全、可维护性 |
| **负责** | 人 | 战略、架构、新颖问题、最终交付 |

### 5. 工作流

1. **描述任务**：自然语言或结构化提示。
2. **执行**：智能体用标准工具（编辑器、CLI、脚本、技能）产出代码/配置/文档。
3. **审查与反馈**：人审 PR，给结构化反馈。
4. **迭代**：智能体按反馈修改直至达标。

---

## 三、在新项目中使用的步骤

1. **复制本模板**  
   - 将 `docs/HARNESS_ENGINEERING_TEMPLATE.md` 复制到新项目的 `docs/`（或保留为参考）。
   - 将 `.cursor/rules/harness-engineering.mdc` 复制到新项目的 `.cursor/rules/`。

2. **创建 AGENTS.md**  
   - 在仓库根目录新建 `AGENTS.md`，按「二、1」填写：目标、规范链接、文档索引、架构边界、工作流提示；总行数控制在约 100 行内。

3. **整理 docs/**  
   - 按「二、2」建立子目录或至少明确：架构、设计、计划、参考资料所在位置，并在 AGENTS.md 中索引。

4. **定义依赖层级**  
   - 在 ARCHITECTURE 或设计文档中写明层级（如 Types → Config → … → UI），配置 Lint/CI 校验（若已有工具链）。

5. **启用规则**  
   - 确保 Cursor 使用 `.cursor/rules/harness-engineering.mdc`（通常放入 rules 目录即生效，必要时在 Cursor 设置中确认规则已加载）。

---

## 四、可选增强

- **可观测性**：将日志/指标/追踪以 LogQL、PromQL 或约定格式暴露给智能体；在隔离环境中复现缺陷并自动验证修复。
- **文档 CI**：定期检查文档与代码的交叉引用、过期标注、目录结构。
