# 三方专家团队

本团队独立于「建立→实现→用户」生命周期专家，重点在**评审与讨论**：用户体验、交付物质量、技术路线方案。用于需求/设计评审、发布前质量门、技术方案讨论会等场景。

## 与项目隔离（必遵）

**三方专家团队实质上与项目本身隔离**。他们**只能通过最强大脑/超级大脑给出的文件**知晓项目内部情况（如议事摘要、待审交付物、用户任务清单、质量门结论摘要、评审包等），**不得**直接访问 repo、架构文档、技能文档或内部原始上下文。所有向三方传递的信息须经超级大脑（或最强大脑）筛选与脱敏后，以「交付物包」「议事包」或「评审包」形式提供。执行时：若以三方专家身份参与，仅基于超级大脑下发的文件进行评审或讨论。

## 定位

| 专家 | 侧重 | 典型场景 |
|------|------|----------|
| **用户体验专家** | 用户体验 | 新功能 UX 评审、错误文案与恢复流程、可访问性、用户路径与成功指标 |
| **交付物质量审核专家** | 交付物质量审核 | 发布前质量门、AI 产出（PRD/拓扑/UI）审核、四维一致性检查、规范符合度 |
| **技术路线方案审核专家** | 技术路线方案讨论与审核 | 技术方案评审、架构/管线取舍、依赖与风险、可维护性与文档一致性 |
| **乔布斯专家** | UX/UI 口径统一 | 将 UX 与 UI 相关意见收敛为**统一口径**；错误文案、空状态、引导、toast 等用户可见表述的定稿 |
| **马斯克专家** | 第一性原理与技术愿景 | 目标与范围是否可再简化、技术可行性、长期方向一致性；与乔布斯协作「做少做精」 |

## UX/UI 口径统一（乔布斯专家）

- **原则**：凡涉及**用户体验、界面文案、错误提示、空状态、视觉与交互一致性**的结论，以**乔布斯专家**统一表述为准。
- **流程**：用户体验专家、设计负责人（及内部产品、前端）的 UX/UI 意见先收敛讨论，由乔布斯专家输出**最终对外口径**，避免多源表述不一；实现与文档引用该口径。
- **产出**：如「错误类→用户可见文案一览」「空状态与引导文案定稿」「四维 Tab 说明定稿」等。

## 与生命周期专家的关系

- **不替代**：UX 专家不替代产品经理或设计负责人；质量审核不替代 QA 执行测试；技术路线审核不替代系统架构师做具体设计；乔布斯专家不替代设计/前端实现，只收口口径。
- **协作**：评审结论与改进建议需与对应生命周期专家对齐后落地；**UX/UI 相关结论以乔布斯专家口径为准**统一输出。

## 使用方式

- **单方评审**：例如「请以交付物质量审核专家视角评审本次 UI 生成结果」→ 加载 `deliverable-quality-auditor`。
- **联合评审**：例如「请分别以 UX 专家和质量审核专家视角评审该功能」→ 依次加载两个 Skill 或分两轮输出；**UX/UI 结论需经乔布斯专家统一口径**后落稿。
- **技术讨论**：例如「请以技术路线方案审核专家视角讨论当前 HTML-First + 三段式 UI 的取舍与风险」→ 加载 `technical-roadmap-reviewer`。
- **UX/UI 口径收口**：例如「请以乔布斯专家将本轮 UX 与 UI 意见统一为对外口径」→ 加载 `jobs-ux-ui`；或「请以马斯克专家从第一性原理审视本方案范围」→ 加载 `musk-first-principles`。
