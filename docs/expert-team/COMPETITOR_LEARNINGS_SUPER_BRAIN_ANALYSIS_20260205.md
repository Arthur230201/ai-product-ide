## 一、马斯克视角（第一性原理）收敛

### 1.1 本质问题是什么

- 本站点的核心价值：**从想法/PRD/画布到可用的 View（及 Spec/Impl）**，且**四维一致、可追溯**。竞品借鉴必须服务于「更短路径、更可预期产出、更可解释」，而不是功能堆砌。
- **可删则删**：凡不能一句话说清「用户得到什么」「为何本站点需要」的，一律延后或不做。例如：Figma 导入（C3）、多形态 CLI/桌面（T5）在未验证需求前不进入本期。

### 1.2 目标能否一句话说清

- **本期可执行目标**：  
  「在不大幅改架构的前提下，把竞品中与**路径更短、错误更可操作、阶段更可感**相关的点收敛为少量可落地项，并明确哪些留给后续。」
- **不纳入本期**：开源叙事（E1/E2/E3）、免费额度（U1）、多模型分工（T6）、完整应用级生成（P3）——均为战略或大改动，需单独立项或路线图。

### 1.3 建议的采纳边界（马斯克侧）

| 建议采纳（本期可讨论落地） | 理由 |
|----------------------------|------|
| P5 主路径入口聚合 / 空白画布 CTA | 与「做少做精」一致：减少入口分散，一句话能说清「先做什么」。 |
| T2 透明变更审查（生成前可审） | 降低「生成即覆盖」的不可逆感；可先做「预览再应用」的最小版。 |
| T1 强化阶段 + 技术栈约束 | 已有三阶段与 Tailwind，仅需与质量门、Stage Marker 成文对齐，无新架构。 |
| C1 阶段产出物可查看/回滚 | 与现有「固定 artifact 目录」可结合，增强可观测与可回滚。 |
| C2 画布模板/引导 | 空状态与模板可合并为「空白画布引导 + 可选模板」，范围可控。 |
| U2 / U3 | 已有多轮共识，按乔布斯口径执行即可。 |

| 有条件采纳（需两轮讨论定范围） | 条件 |
|--------------------------------|------|
| P1 更短路径（描述→组件一站式） | 与现有「想法→拓扑→节点→View」是否并存、谁为主路径，需产品与 UX 决议。 |
| P2 对话式迭代改 UI | 与「节点内编辑 + 重新生成」的边界；可先限定为「对当前节点 View 的自然语言改」且不替代全量重生成。 |
| T3/T4 多 LLM 与隐私 | 本站点已有基础；讨论重点为「成文表述」与「本地/内网部署文档」，不扩大实现范围。 |

| 建议不采纳（本期） | 理由 |
|--------------------|------|
| P3 完整应用级一次生成 | 架构与粒度变化大，非最小必要；保持「单节点/单次生成」为默认。 |
| T5 终端/桌面多形态 | 无当前需求验证，属扩展形态，记入路线图。 |
| T6 多模型按阶段分工 | 增加配置与运维复杂度；本期不采纳，可后续做 A/B 或实验。 |
| C3 Figma 导入 | 输入源扩展，非核心路径，后续迭代。 |
| E1/E2/E3、U1 | 战略与商务，不进入「可借鉴点落地」讨论。 |

## 二、乔布斯视角（体验与口径）收敛

### 2.1 用户看到什么、第一步做什么

- **入口与主路径**：采纳 P5 与 C2，使用户「首屏即知：输入想法或上传文档开始生成，或按 Tab 添加节点」；不增加新概念，仅收敛现有入口与空状态文案（与既有乔布斯口径一致）。
- **错误与阶段**：U2、U3 已定稿，实现时严格引用「最终执行版口径」；长耗时阶段文案与 Stage Marker、质量门一一对应，避免多源表述。

### 2.2 产品气质与一致性

- **不堆功能**：不因竞品有「对话式改 UI」「Figma」就立刻加；先做「预览再应用」（T2）和「阶段可感」（U2），保证每一步都可解释、可操作。
- **四维 Tab**：保留 View/Spec/Impl/Test，tooltip 用中文短说明（界面/需求/实现/测试），与现有乔布斯口径一致；不做竞品式「单维代码」化。

### 2.3 建议的采纳边界（乔布斯侧）

| 采纳并与口径对齐 | 说明 |
|------------------|------|
| P5、C2 | 空状态与入口收敛为已定稿的「输入想法或上传文档，开始生成」+「或按 Tab 添加节点」；主操作聚合不新增术语。 |
| U2、U3 | 完全按 `UX_THIRD_PARTY_REVIEW.md` 最终执行版口径实现。 |
| T2（预览再应用） | 若做，文案需经乔布斯口径：如「预览变更」「应用」「放弃」；错误态统一为可操作一句。 |

| 需两轮讨论再定口径 | 说明 |
|--------------------|------|
| P1、P2 | 若做「描述→组件」或「对话改 UI」，需明确用户可见的步骤与文案，由乔布斯专家在两轮讨论后收口。 |

## 四、争议与需裁决点（供乔布斯与马斯克最终裁决）

1. **主路径**：保留「想法→拓扑→节点→View」为主，还是增加「描述→组件」为并列主路径？若并列，入口如何不分散？（马斯克：能一句话说清；乔布斯：用户第一步不困惑。）
2. **对话式改 UI**：做「仅当前节点 View 的自然语言改」是否纳入本期？若纳入，与「重新生成」的边界与文案由乔布斯收口。
3. **预览再应用**：是否所有「写 View 代码」的生成都需「预览→确认→应用」？还是仅「覆盖已有内容」时强制预览？（涉及实现量与体验一致性。）
