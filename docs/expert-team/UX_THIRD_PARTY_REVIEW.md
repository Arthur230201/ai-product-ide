# 第三方用户体验专家审核报告与优化方案

**审核方式**：最强大脑牵头，邀请**独立第三方用户体验专家团队**对当前应用进行 UX 专项审核；两轮讨论后形成报告与优化方案，最强大脑裁决后交**内部团队**审核是否执行。

**团队构成**：  
- **三方团队**：用户体验专家、交付物质量审核专家、技术路线方案审核专家、**乔布斯专家**（UX/UI 口径统一）、**马斯克专家**（第一性原理）。  
- **内部团队**：产品经理、设计负责人、前端/画布工程师、**乔布斯专家**、**马斯克专家**。  
- **口径约定**：凡 **UX 与 UI 相关**的结论与表述（错误文案、空状态、引导、Tab 说明、toast 等），以**乔布斯专家**统一意见为准，避免多源表述不一。

**审核范围**：用户路径、错误与恢复、界面清晰与一致性、首屏与加载、空状态与引导、可访问性。

---

## 第一轮讨论：第三方专家视角发现

### 1. 用户路径与心智模型

- **进入→生成→编辑→预览/导出** 主路径存在，但 **入口分散**：CommandBar、ProjectToolbar、NodeDetailPanel、ProjectBlueprint 等多处可触发「生成拓扑 / 生成 UI / 生成 PRD」，新用户难以建立「先做什么、再做什么」的心智；建议在**首次使用或空白画布**时提供简短引导（如「从左侧描述想法生成拓扑，或从顶部上传文档/图片」）。
- **四维 Tab（View / Spec / Impl / Test）** 对非技术用户认知负荷高；当前无 Tab 内说明或 tooltip，用户可能不理解「Spec 从 View 反推」「Impl 从 Spec 派生」。建议在 NodeDetailPanel 各 Tab 增加**一句话说明**或帮助图标。
- **同步状态（已同步/未同步）** 在节点或详情中展示时，用户易误解为「数据有问题」；与既有 JOINT_REVIEW 结论一致，需在 UI 或帮助中说明「表示上次更新来源，非实时四维一致」。

### 2. 错误与恢复体验

- **错误文案不统一**：CommandBar 中 UI 生成失败用 `toast.error('❌ UI代码生成失败', { description: errorMessage })`，NodeDetailPanel 中美化/交互失败为「美化失败，请稍后重试」「添加交互失败，请稍后重试」；**AI 错误类型**（RATE_LIMIT / NETWORK / PROVIDER / PARSE）未在前端映射为可操作建议（如 429 显示冷却秒数、网络失败建议检查网络、解析失败建议简化描述）。
- **长时间等待反馈**：生成拓扑、三段式 UI、生成 PRD 等为长耗时操作；部分路径有 loading toast，但**进度感不足**（无阶段提示如「正在生成静态结构…」「正在美化样式…」），超时后仅提示「请求超时」或技术信息，用户不知道「重试」还是「简化输入」。
- **降级与 fallback**：拓扑失败有 fallback 图、UI 失败有「保留原 code」策略，但**用户侧**是否明确被告知「已使用备用方案」及「下一步可编辑或重试」需确认；否则用户可能以为「没生成出来」而重复点击。

### 3. 界面清晰与一致性

- **术语与命名**：画布、节点、边、详情面板、命令栏、项目蓝图等命名在代码与文档中一致，但**中英混用**（如「Full PRD HTML 导出」）与**按钮动词不统一**（「生成」「创建」「导出」混用）可能影响扫读效率；建议统一主操作动词与次要操作区分。
- **空状态**：空白画布、无选中节点、无 View 代码时的**空状态**是否有明确文案与引导（如「点击画布空白处添加节点」或「选择节点后在右侧编辑」）；若仅留白或占位图，新用户易卡在第一步。
- **成功反馈**：部分操作有 `toast.success`（如「加载完成」「美化完成」「项目已保存」），**加载完成**使用固定 2 秒后消失的绿条，与 sonner 的 toast 风格是否统一；且「加载完成」是否必要（用户未主动请求）可商榷，避免打扰。

### 4. 首屏与加载

- **Hydration 等待**：首屏依赖 StoreHydration，500ms 超时后强制展示画布；**加载中**仅「加载中…」「正在初始化画布…」与 spinner，无进度或预估时间；大图或慢设备可能仍感「卡顿」，建议考虑「超过 N 秒显示更多说明或跳过引导」。
- **加载完成提示**：当前「加载完成」绿条在每次进入（含已缓存）都会短时显示；若用户频繁刷新或多 Tab，可能造成干扰；可改为**仅首次加载完成**时展示，或弱化为更小范围提示。

### 5. 可访问性与包容性

- **错误页与重试**：error.tsx、global-error.tsx、ErrorBoundary 均提供「重试」按钮与错误信息，**错误 ID（digest）** 已展示，便于支持排查；但**键盘焦点**是否在「重试」上、焦点顺序是否合理需在可访问性自检中确认。
- **toast 与屏幕阅读器**：sonner toast 的 `description` 是否被读屏正确播报、toast 消失后焦点是否回到触发操作的控件，建议在 a11y 检查中覆盖。

### 6. 反馈闭环与成功指标

- **用户在某步流失**：当前无埋点或可观测在「生成拓扑成功→生成 UI→编辑→导出」各步的完成率；第三方专家建议在**产品需求或文档**中定义成功指标（如首次成功生成率、各阶段完成率），便于后续迭代与 UX 优化有据可依。

## 第二轮讨论：收敛与优先级

- **一致认同**：错误文案与 AI 错误类型映射（429/网络/解析）应统一为**可操作建议**；「同步状态」含义需在 UI 或帮助中说明；长耗时操作应增强**阶段/进度感**（至少文案如「正在生成…」分阶段）；空白画布/空状态需有**明确引导**。
- **一致认同**：四维 Tab 对新手不友好，建议**一句话说明或帮助图标**；首屏「加载完成」可收敛为仅首次或弱化。
- **分歧与取舍**：
  - **埋点与成功指标**：第三方专家建议成文并预留埋点；内部可接受「先成文定义，实现排期」，不强制本次上线埋点。
  - **可访问性**：第三方建议对错误页与 toast 做 a11y 自检；内部建议列入「后续迭代」或与全局 a11y 一起做。
  - **引导与 onboarding**：第三方希望「首次使用/空白画布」有引导；产品与前端建议先做**空状态文案 + 入口说明**，完整 onboarding 作为后续迭代。

**优先级排序**：  
- **P0**：错误文案与 AI 错误类型→可操作建议统一；同步状态说明（NodeDetailPanel 或帮助）。  
- **P1**：长耗时操作阶段/进度文案；空白画布与无选中节点的空状态引导；四维 Tab 一句话说明。  
- **P2**：首屏「加载完成」仅首次或弱化；成功指标成文（含后续埋点）；可访问性自检列入 backlog。

## 乔布斯再次审核与三方团队两轮商议

### 乔布斯再次审核意见（第一轮）

乔布斯专家对既有优化方案与口径进行二次审核，提出以下修改建议：

1. **错误文案**：每条只做**一件事**——告诉用户「发生了什么」+「下一步做什么」。当前「请求过于频繁，请 X 秒后重试」已合格；「生成结果解析失败，请尝试简化描述或重试」中「简化描述或重试」二选一易让用户犹豫，建议收敛为**一句主建议**：「请简化描述后重试」或「请重试」。
2. **同步状态说明**：「同步状态表示上次更新来源，不代表实时四维一致」中「四维一致」偏技术，普通用户无需理解；建议改为**人话**：「仅表示最近一次更新来源，非实时同步。」
3. **空白画布引导**：当前两句（输入想法/上传文档 + 点击/Tab 添加节点）信息量偏大；**首句即行动**：「输入想法或上传文档，开始生成」；第二句缩短为「或按 Tab 添加节点」。
4. **四维 Tab 说明**：主界面用**极短标签**（如 View→「界面」、Spec→「需求」、Impl→「实现」、Test→「测试」），详细说明放 tooltip，避免副标题抢主内容。
5. **加载完成**：即使用户未主动请求，首次加载完成给予**极轻量确认**即可：文案改为「已就绪」，1 秒消失、右下角小字，不抢注意力；非首次不展示。

### 三方团队回应与第二轮商议

- **用户体验专家**：同意同步状态改为「非实时同步」、错误主建议收敛为一句；空白画布首句「输入想法或上传文档，开始生成」更清晰。建议 Tab 主界面保留 View/Spec/Impl/Test 英文（与代码/文档一致），tooltip 用中文短说明即可，避免中英混用。
- **交付物质量审核专家**：错误类映射与阶段 loading 文案需在实现时与 Stage Marker、质量门一致；同意乔布斯对「一句主建议」的收敛，便于审核时检查「每处错误是否仅展示一条可操作建议」。
- **技术路线方案审核专家**：无异议；建议最终口径成文后，前端统一工具函数（如 `getUserFacingErrorDescription`）的返回值与本文档「最终执行版」一一对应，便于维护。

**乔布斯与三方共识（第二轮结论）**：  
- 采纳乔布斯对同步状态、空白画布首句、加载完成「已就绪」的简化；错误类 PARSE 主建议统一为「请简化描述后重试」；Tab 主界面保持 View/Spec/Impl/Test，tooltip 用中文短说明（界面/需求/实现/测试）。  
- 以上收敛为**最终执行版口径**，见下节；实现与文档仅引用该版。

## 最终修改意见与最终执行版口径

### 最终修改意见（乔布斯 + 三方共识）

| 项 | 原表述 | 最终修改后 |
|----|--------|------------|
| 同步状态说明 | 同步状态表示上次更新来源，不代表实时四维一致。 | **仅表示最近一次更新来源，非实时同步。** |
| 空白画布主文案 | 从左侧输入想法生成拓扑，或从顶部上传文档/图片 | **输入想法或上传文档，开始生成。** |
| 空白画布次句 | 点击此处或使用 Tab 键添加节点 | **或按 Tab 添加节点** |
| 无选中节点 | 请先选择画布上的节点 | 不变 |
| PARSE 错误 | 生成结果解析失败，请尝试简化描述或重试 | **生成结果解析失败，请简化描述后重试。** |
| 其他错误类 | RATE_LIMIT/NETWORK/PROVIDER 文案 | 不变 |
| 四维 Tab | 副标题长句 | **Tab 标签保持 View/Spec/Impl/Test；tooltip 中文短说明：界面 / 需求 / 实现 / 测试** |
| 加载完成 | 加载完成（2 秒绿条） | **仅首次：文案「已就绪」，右下角小字 1 秒消失；非首次不展示。** |

### 最终执行版口径（乔布斯与三方共识，供实现与文档引用）

以下为**唯一对外口径**，实现时以本段为准。

- **错误类→用户可见文案**  
  - RATE_LIMIT / 429 → 「操作过于频繁，请 X 秒后重试」（有 cooldownSeconds 时展示秒数）。  
  - NETWORK → 「网络异常，请检查网络后重试。」  
  - PROVIDER → 「服务暂时不可用，请稍后重试。」  
  - PARSE → 「生成结果解析失败，请简化描述后重试。」  
  - 不向用户展示原始 error.message；技术信息仅开发环境或日志。
- **同步状态说明**（tooltip/帮助）  
  - 「仅表示最近一次更新来源，非实时同步。」
- **空状态与引导**  
  - 空白画布主文案：「输入想法或上传文档，开始生成。」次句：「或按 Tab 添加节点。」  
  - 无选中节点：「请先选择画布上的节点。」  
  - 四维 Tab：标签保持 View / Spec / Impl / Test；tooltip 中文短说明依次为「界面」「需求」「实现」「测试」。
- **长耗时**  
  - loading 分阶段：如「正在生成静态结构…」「正在美化样式…」「正在添加交互…」；生成拓扑/PRD 为「正在生成拓扑…」「正在生成 PRD 文档…」。
- **首屏加载完成**  
  - 仅首次进入且 hydrate 完成时展示；文案「已就绪」，右下角小字、1 秒消失；非首次或缓存恢复不再展示。

## 优化方案（供最强大脑裁决与内部团队审核）

### 方案 A：错误与恢复体验（P0，建议执行）

1. **AI 错误类型→用户可操作文案**  
   - 在前端（如 CommandBar、NodeDetailPanel 及所有调用 AI 的入口）统一，**以「最终执行版口径」为准**：  
     - `RATE_LIMIT` / 429 → 「操作过于频繁，请 X 秒后重试」（若有 cooldownSeconds 则展示）。  
     - `NETWORK` → 「网络异常，请检查网络后重试。」  
     - `PROVIDER` → 「服务暂时不可用，请稍后重试。」  
     - `PARSE` → 「生成结果解析失败，请简化描述后重试。」  
   - 所有 `toast.error` 的 description 优先使用上述映射，避免直接展示原始 error.message（技术栈信息可仅开发环境或日志）。建议抽成统一工具函数（如 `getUserFacingErrorDescription`）复用。
2. **同步状态说明**  
   - 在 NodeDetailPanel 或节点「未同步」展示处增加 tooltip/帮助文案：**「仅表示最近一次更新来源，非实时同步。」**

### 方案 B：长耗时与空状态（P1，建议执行）

3. **长耗时操作阶段/进度文案**  
   - 三段式 UI：若已有「生成中」toast，增加分阶段描述（如「正在生成静态结构…」「正在美化样式…」「正在添加交互…」），或至少在单一 loading 文案中体现阶段感。  
   - 生成拓扑、生成 PRD：loading 文案明确为「正在生成拓扑…」「正在生成 PRD 文档…」，超时或失败时 toasts 与「重试 / 简化描述」等建议一致。
4. **空白画布与无选中节点**  
   - 空白画布：在画布中央或显眼处展示**空状态文案 + 引导**（以「最终执行版口径」为准）：主文案「**输入想法或上传文档，开始生成。**」次句「**或按 Tab 添加节点**」。  
   - 无选中节点时右侧详情区：**「请先选择画布上的节点。」**
5. **四维 Tab 说明**  
   - 标签保持 View / Spec / Impl / Test；在 Tab 上增加 **tooltip 中文短说明**：View→「界面」、Spec→「需求」、Impl→「实现」、Test→「测试」。详细说明可放在帮助或副标题，不抢主内容。

### 方案 C：首屏与成功提示（P2，建议执行）

6. **「加载完成」提示收敛**  
   - 仅**首次**进入应用且 Store 完成 hydrate 时展示；文案改为**「已就绪」**，右下角小字、**1 秒消失**；若来自缓存或非首次，不再展示。避免与 sonner 主 toasts 抢注意力。

### 方案 D：成功指标与可访问性（P2，记录为后续迭代）

7. **成功指标成文**  
   - 在 `docs/` 或产品需求中新增「成功指标与观测」短文：定义首次成功生成率、各阶段完成率、关键流失步骤等；埋点与实现由产品与前端排期。
8. **可访问性自检**  
   - 将 error 页、ErrorBoundary、toast 的键盘焦点与读屏支持列入 **后续优化清单**，与全局 a11y 一起排期。

## 最强大脑裁决

**结论**：方案 A、B、C 均为**直接改善用户可见体验**（错误可理解、有下一步、空状态有引导、长流程有进度感），且单点改动范围可控；方案 D 不改变本次交付行为，仅成文与 backlog。  
**裁决**：**批准方案 A、B、C 提交内部团队审核是否执行**；方案 D 仅记录为后续迭代。若内部团队（产品、设计、前端）无反对意见或仅提出可接受的修订，则**按 A → B → C 顺序执行**；方案 D 写入「后续优化清单」。
