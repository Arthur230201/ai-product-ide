# 两项目合体方案：专家讨论与最终结论

> **目标**：将「ai-product-ide」（本项目）与「瞎搞项目」合并统一，提供 13 种（及以上）交付物；先发散 10 轮讨论，再收敛 5 轮，形成可执行合体方案。

---

## 一、两项目基本信息

### 1.1 ai-product-ide（本项目）

| 维度 | 内容 |
|------|------|
| **定位** | AI-Native 产品 IDE：画布 + 四维节点，统一 UI / PRD / 实现 / 测试为单一事实源 |
| **核心逻辑** | 想法 → 图 → 界面 → 需求 → 实现 → 测试（Map → UI → Doc → Code） |
| **数据结构** | **Fractal Node**：每节点 4 个 Tab — View(可运行 UI)、Spec(需求)、Impl(API/DB)、Test(测试用例) |
| **输入方式** | 文本生成图、文档/PRD 解析成图、Figma/截图生成图 |
| **已有导出** | PRD(HTML/Word/Markdown)、需求规格说明书(SRS Word)、测试报告(12 章 Word)、系统设计说明书(14 章 Word)、使用说明书(5 章 Word) |
| **技术栈** | Next.js 14、React Flow、Zustand、Tailwind、Vercel AI SDK；前端为主，状态在客户端 |
| **优势** | UI/PRD/测试/系统设计在节点级精细化、标准章节目录、多格式导出、画布与节点强绑定 |

### 1.2 瞎搞项目（evidence-to-prd）

| 维度 | 内容 |
|------|------|
| **定位** | 乙方主线到 PRD：证据 → 事实 → 投影，一体化 Web App |
| **核心逻辑** | 证据文件(PDF/DOCX/PPTX等) → EvidenceChunk(锚点) → Fact(需求/规则/API等) → Projection(PRD/标书/方案等) → 导出 HTML 包 |
| **数据结构** | **三层**：Evidence(文件/片段) → Facts(结构化事实+关系+版本) → Projection(Chapter/Block/Asset) |
| **交付物** | **13 种**：assessment、req_plan、charter、tech_req、tender_pack、bid、solution、prd、srs、implementation_plan、test_cases、test_report、ops_manual |
| **专家审计** | 每种交付物对应独立专家，对**导出 HTML** 做行业标准符合度评分（结构/内容/可追溯性等） |
| **技术栈** | Express、better-sqlite3、client(Vite/React)、迭代脚本(Playwright/Vitest)、shared/config(deliverables.l3.json) |
| **优势** | 13 种交付物覆盖标前到交付全链路、证据溯源、事实版本与关系、专家评分与迭代闭环、离线 HTML 导出 |

### 1.3 对比小结

| 对比项 | ai-product-ide | 瞎搞项目 |
|--------|----------------|----------|
| 数据重心 | 画布节点（View/Spec/Impl/Test） | 证据+事实+投影（DB 与文件） |
| 交付物数量 | 5 类已实现 + 路线图扩展 | 13 类已实现 + 专家审计 |
| 导出形态 | Word/HTML/Markdown，标准章节 | 以 HTML 包为主，Block/Asset |
| 质量保障 | 无自动化评分 | 13 专家对导出物评分、迭代达标 |
| 适用场景 | 产品/研发从 0 到 PRD+设计+测试 | 乙方从招标到交付的全文档流 |

## 二、发散讨论（10 轮）：以乔布斯、马斯克为首的专家团队

**参与角色**：乔布斯（产品与体验）、马斯克（第一性原理与工程）、产品专家、架构师、交付专家、测试专家、运维专家。

---

### 第 1 轮：一个项目全生命周期里，交付物到底有哪些？

- **马斯克**：从「合同/招标」到「上线运维」，每一步的**可交付成果**列出来，不要漏。
- **交付专家**：标前 → assessment（评估报告）、req_plan（需求计划）、charter（项目章程）、tech_req（技术需求）、tender_pack（招标文件）；投标 → bid（标书）；中标后 → solution（解决方案）、prd（PRD）、srs（需求规格）、implementation_plan（实施计划）；开发与验收 → test_cases（测试用例）、test_report（测试报告）；交付与运维 → ops_manual（运维手册）。还有**使用说明书**给最终用户。
- **乔布斯**：用户要的是「能用的产品」和「能读的说明」；**使用说明书**必须算一种交付物，且要好看、好懂。
- **结论**：至少 13+1=14 种；若再拆「系统设计说明书」「API 文档」「发布说明」等，可到 17～20 种。

---

### 第 2 轮：每种交付物「以什么方式使用」？

- **产品专家**：PRD/SRS 给研发与评审；测试报告给 QA 与项目经理；系统设计/运维手册给研发与运维；使用说明书给客户与支持；标书/招标文件给采购与评标；评估报告/项目章程给立项与决策。
- **马斯克**：每份文档都要有**单一用途**：要么是合同/合规依据，要么是执行依据（开发/测试/运维），要么是沟通依据（客户/干系人）。混在一起就会没人看。
- **乔布斯**：使用说明书 = 产品的一部分，不是「附赠手册」；要可检索、可截图、可随版本更新。
- **结论**：为每种交付物明确「谁用、在什么阶段用、解决什么问题」，合体后的系统应支持「按角色/阶段」筛选导出清单。

---

### 第 3 轮：能否再拓展更多交付物？

- **架构师**：API 文档、数据库设计/DDL、部署架构图、环境清单、配置项说明、安全/隐私评估清单、发布说明(Release Notes)、验收清单(RTM/交付清单)。
- **测试专家**：测试计划、测试方案、缺陷报告汇总、性能测试报告、安全测试报告；可与「测试报告」合并或拆子类型。
- **马斯克**：拓展的前提是**有稳定数据来源**；不能为凑数而造空壳文档。画布节点已有 spec/impl/test，可衍生出 API 文档、DDL、测试用例集、验收清单；证据/事实层可衍生出评估、标书、实施计划。
- **乔布斯**：宁可少而精：先保证 13～15 种**有内容、有标准**，再按需加「竞品对比」「演示脚本」「培训大纲」等。
- **结论**：拓展到 15～20 种合理；新增项需对应到「数据从哪来、谁维护、导出模板是什么」。

---

### 第 4 轮：本项目的优点如何保留并放大？

- **产品专家**：ai-product-ide 的**画布+四维节点**是强项：一个节点 = 一个页面/模块，View/Spec/Impl/Test 同源，无漂移。合体后应保留为「产品/研发侧」的主编辑界面。
- **乔布斯**：PRD/测试报告/系统设计/使用说明书已有**标准章节目录**（12 章、14 章等），这是专业度；合并后这些标准要成为「默认模板」，不能退化成随便几段话。
- **架构师**：导出格式 Word+HTML+Markdown 满足不同场景（评审/归档/Confluence）；应保留多格式，并可对 13 种交付物逐步覆盖。
- **结论**：合体以**画布与节点**为产品/研发侧主数据源；保留并推广「标准章节」与多格式导出。

---

### 第 5 轮：瞎搞项目的优点如何保留并放大？

- **交付专家**：瞎搞的 **13 种交付物 + 13 专家** 覆盖了从评估到运维的完整链路；合体后这 13 种应全部纳入「交付物目录」，并保留「按行业标准评分」的思路。
- **马斯克**：**证据→事实→投影** 的链条适合「有大量既有文档」的乙方场景：上传标书、需求、合同，抽事实，再生成各类投影。合体后应保留这条链路，作为「证据驱动」模式，与「画布驱动」模式并存。
- **架构师**：专家审计是对**导出结果**做质量门禁，而不是只看 UI 有没有按钮；这能驱动内容真实达标。合体后应对关键交付物（至少 PRD、SRS、测试报告、标书）做「导出物专家评分」可选能力。
- **结论**：保留 13 种交付物定义与专家标准；保留证据/事实层作为可选数据源；引入「导出物专家审计」作为质量闭环。

---

### 第 6 轮：两套数据模型如何统一？

- **马斯克**：第一性原理——**产出物**是什么？是「文档」（PRD、测试报告、标书…）。**输入**是什么？要么是「画布节点」（View/Spec/Impl/Test），要么是「证据+事实」（文件→Fact→关系）。所以统一模型 = **统一「文档」的生成输入与输出**，而不是强行把两种输入揉成一个表结构。
- **架构师**：建议**双源 + 统一投影**：  
  - 源 A：画布（nodes + projectMeta + globalRules）→ 用于 PRD、SRS、测试报告、系统设计、使用说明书、API 文档等。  
  - 源 B：证据+事实（Evidence/Fact/Relation）→ 用于 assessment、req_plan、charter、tech_req、tender_pack、bid、solution、implementation_plan、ops_manual 等。  
  - 投影层：统一为「交付物类型 + 章节/Block + 导出路径」；导出时按类型选源 A 或源 B 或混合。
- **乔布斯**：用户不关心底层是「节点」还是「事实」；用户关心的是「我要标书」「我要测试报告」——一键导出、格式正确、内容达标。
- **结论**：采用「双源 + 统一交付物目录 + 按类型选源」；不强行把画布写进 SQLite 或把事实写进 Zustand，通过「适配器」生成统一投影。

---

### 第 7 轮：技术栈与仓库结构如何选？

- **架构师**：两项目技术栈不同（Next.js vs Express+Vite）。合体若选**单仓**：以 Next.js 为主，Express 作为 API 子服务或 BFF 调用证据/事实/投影接口；或把证据/事实/投影迁到 Next API + SQLite/Postgres。若选**双仓**：ai-product-ide 为前端+画布主应用，瞎搞为「交付物引擎」服务，通过 HTTP 调用生成 13 种导出与专家评分。
- **马斯克**：优先**单仓、单一入口**：一个产品一个 repo，减少「两个系统」的心智负担；内部用模块边界区分「画布域」与「证据/事实域」。
- **乔布斯**：前端体验必须统一：一个 URL、一种导航、一套设计语言；不能导出时跳转到「另一个系统」的界面。
- **结论**：倾向**单仓合并**，以 ai-product-ide 为主壳（Next.js），将瞎搞的 13 种交付物生成与专家审计以服务/模块形式接入；或先**双仓 + 集成**，再逐步迁核心到单仓。

---

### 第 8 轮：13 种交付物与现有 5 类导出的映射关系？

- **交付专家**：  
  - prd ↔ 现有 PRD 导出；solution ↔ 系统设计说明书（可扩展章节）；srs ↔ 需求规格说明书；test_cases ↔ 测试报告中的用例表；test_report ↔ 测试报告全文；ops_manual ↔ 运维手册（当前为路线图项，可新增）。  
  - assessment、req_plan、charter、tech_req、tender_pack、bid、implementation_plan：当前画布无直接数据，需从「证据/事实」或从「项目蓝图+新表单」生成；或先做模板+占位，由用户后续填写。
- **乔布斯**：能直接从画布生成的（PRD、SRS、测试报告、系统设计、使用说明书）必须**优先做精**；其余 8 种可「先有模板与入口，再逐步接数据」。
- **结论**：5 类已有导出与 13 种中的 5～6 种对齐；其余 7～8 种通过「证据/事实」或「蓝图+模板」补齐，并统一进同一「交付物」菜单。

---

### 第 9 轮：专家评分放在哪一层？

- **测试专家**：专家评的是**导出后的文件**（HTML/Word），不是编辑中的草稿；所以评分应在「导出」之后触发，或由 CI/迭代脚本调用。
- **马斯克**：评分 = 质量门禁；未达标可阻断发布或标红提示。合体后「导出」动作可带可选参数：是否运行专家审计；若运行，则返回分数与问题列表，并可写入项目元数据。
- **产品专家**：ai-product-ide 当前无评分；瞎搞有 13 专家。合并后至少对 PRD、测试报告、系统设计、SRS 引入轻量评分（如结构完整性、必备章节是否存在），不一定要全量上 13 套权重。
- **结论**：专家审计作为「导出后」的可选步骤；先实现 4～5 种核心交付物的评分，再扩展到 13 种。

---

### 第 10 轮：优先级与 MVP 合体范围？

- **乔布斯**：第一版合体 MVP = 一个入口、一个「交付物」列表、画布驱动的 5 类导出保持现有体验，并新增「交付物目录」中其余类型的占位或模板导出；证据/事实链路可作为「高级模式」或二期。
- **马斯克**：MVP 必须能**闭环**：至少一种非画布交付物（如 assessment 或 bid）从证据/事实生成并导出，证明双源可行；否则只是「把两个菜单拼在一起」。
- **架构师**：阶段一：统一「交付物」菜单，13 种全部有入口，其中 5 种走现有画布导出，8 种走「模板+占位」或跳转说明。阶段二：接入证据/事实引擎，实现 8 种中 2～3 种的真实生成。阶段三：专家评分接入与迭代闭环。
- **结论**：MVP = 交付物目录 13 种可见 + 5 种画布导出不变 + 其余 8 种模板/占位或简要说明；二期接证据/事实 + 2～3 种真实生成；三期专家评分与迭代。

## 三、收敛讨论（5 轮）：形成最终方案

---

### 收敛第 1 轮：交付物清单拍板

- **共识**：**至少 13 种交付物**，与瞎搞一致；并增加**使用说明书**为第 14 种。允许后续扩展至 15～20 种（API 文档、发布说明、验收清单、演示脚本等）。
- **清单**：assessment、req_plan、charter、tech_req、tender_pack、bid、solution、prd、srs、implementation_plan、test_cases、test_report、ops_manual、**user_manual**；扩展：api_doc、release_notes、acceptance_checklist、demo_script 等。

---

### 收敛第 2 轮：数据与生成策略拍板

- **共识**：  
  - **画布驱动**（现有）：prd、srs、test_report、system_design、user_manual、test_cases（用例表）、api_doc、release_notes 等，数据来自 nodes + projectMeta + globalRules。  
  - **证据/事实驱动**（迁自瞎搞）：assessment、req_plan、charter、tech_req、tender_pack、bid、solution、implementation_plan、ops_manual，数据来自 Evidence/Fact/Relation；若暂无证据层，则用**项目蓝图 + 模板**生成占位文档，保证 13 种均可导出。  
- **统一**：所有交付物在 UI 上归属同一「交付物」或「导出」体系；导出格式优先 Word/HTML，与现有一致。

---

### 收敛第 3 轮：合体形态拍板

- **共识**：  
  - **形态**：以 **ai-product-ide 为主仓**，保留 Next.js + 画布 + 现有 5 类导出；将瞎搞项目中的「13 种交付物定义、章节/Block 规范、专家评分逻辑」以**模块/服务**形式迁入或通过 API 调用。  
  - **证据/事实层**：若主仓不直接上 SQLite，则可采用「先 API 后迁库」：瞎搞的 server 保留为独立服务，ai-product-ide 通过 fetch 调用其「生成某交付物」「专家评分」接口；待稳定后再将核心表与逻辑迁入 Next.js API + 同一 DB。  
  - **前端**：单一入口、单一导航；「导出」菜单扩展为「交付物中心」或「导出」下列出 13+ 种，每类可多格式（Word/HTML/PDF 等）。

---

### 收敛第 4 轮：实施阶段拍板

- **阶段一（合体 MVP）**：  
  - 在 ai-product-ide 中新增「交付物」概念与配置（如交付物 key、名称、数据源类型：canvas / evidence / template）。  
  - 现有 5 类导出保留并映射为 prd、srs、test_report、system_design、user_manual；新增其余 8 种的导出入口，实现方式可为「模板 Word/HTML + 项目名/版本等占位」或「跳转至说明页」。  
  - 文档与产品说明中明确「13+ 种交付物」及每种的使用方式与数据来源。  
- **阶段二（证据/事实接入）**：  
  - 将瞎搞的 evidence-to-prd 的 server 或核心逻辑以子服务或 Next API 形式接入；实现 assessment、bid、solution、implementation_plan、ops_manual 等至少 2～3 种的**真实生成**（从证据或事实表生成内容）。  
  - 画布与证据可共享 projectMeta；证据层可有独立「项目」与「项目」关联。  
- **阶段三（专家评分与迭代）**：  
  - 对 PRD、SRS、测试报告、系统设计等导出结果调用专家评分（规则迁自瞎搞 deliverable-experts-v2）；在 UI 上展示分数与改进建议，可选「迭代直到达标」。

---

### 收敛第 5 轮：最终方案一句话与检查表

- **一句话**：以 **ai-product-ide 为主产品**，将**瞎搞的 13 种交付物目录与专家审计**纳入，形成「画布驱动 + 证据驱动」双源、**统一交付物导出与可选质量评分**的一体化产品；先实现 13+ 种导出入口与画布侧 5 种精修，再接入证据/事实与专家闭环。
- **检查表**：  
  - [ ] 交付物目录 ≥13 种且含使用说明书；  
  - [ ] 画布驱动的 5 类导出（PRD/SRS/测试报告/系统设计/使用说明书）保持并强化标准章节；  
  - [ ] 其余交付物有导出入口（模板或真实生成）；  
  - [ ] 数据策略明确：画布 vs 证据/事实 vs 模板；  
  - [ ] 合体形态明确：单仓主仓 + 瞎搞模块/服务接入；  
  - [ ] 专家评分可选、先覆盖核心 4～5 种；  
  - [ ] 分阶段实施：MVP → 证据接入 → 评分闭环。

## 四、最终合体方案摘要

1. **交付物**：至少 **13+1=14 种**（瞎搞 13 + 使用说明书），可拓展到 17～20 种；每种明确「谁用、何时用、数据从哪来」。
2. **数据**：**画布**（节点 View/Spec/Impl/Test）驱动 PRD、SRS、测试报告、系统设计、使用说明书、API 文档等；**证据/事实**驱动 assessment、标书、solution、实施计划、运维手册等；缺数据时用**模板+占位**保证可导出。
3. **产品形态**：以 **ai-product-ide 为主仓**，统一入口与导航；瞎搞的 13 种定义、生成逻辑、专家审计以模块或 API 形式接入。
4. **实施**：阶段一 = 交付物目录 + 5 类精修 + 其余 8 种入口（模板/占位）；阶段二 = 证据/事实接入 + 2～3 种真实生成；阶段三 = 专家评分与迭代闭环。
5. **质量**：保留「对导出物做专家评分」的思路，先覆盖 PRD、SRS、测试报告、系统设计等核心交付物，再推广到 13 种。

本文档可作为两项目合并的**产品与架构依据**，后续可拆解为具体任务（目录配置、导出适配、API 设计、专家规则迁移等）进入开发排期。
