# 为何其他应用能生成更好看的 UI？

## 一、核心差距对比

| 维度 | 其他应用（如 v0、Bolt、Stitch） | 本应用现状 |
|------|----------------------------------|------------|
| **输出形态** | 多基于 **组件库**（如 shadcn/ui、Radix）拼装 | **纯手写** div + Tailwind class，每次从零「发明」样式 |
| **设计来源** | 组件自带成熟设计（圆角、阴影、间距、状态） | 完全靠模型根据文字规则生成，一致性差 |
| **结构** | 先布局/结构再样式，或多阶段生成 | 单次生成「布局+样式+内容」一体，容易顾此失彼 |
| **约束方式** | 输出在「已知组件集合」内，质量有上限保证 | 只约束「不要怎样」「要用什么类名」，无「必须长什么样」的具象参照 |
| **示例** | 常带 1–2 个示例组件或截图，模型模仿 | 无示例，仅文字描述（Constitution + Premium Brief） |

**结论**：别人是「用现成的好看积木搭房子」，我们是「让模型自己造砖再搭」——积木质量不稳定，整体观感就容易一般。

---

## 二、可落地的改进（不改架构的前提下）

1. **在 prompt 里注入「组件级代码片段」**  
   给模型 2–3 段可直接模仿的 TSX：例如「主按钮」「卡片」「输入框+标签」的推荐写法（Tailwind 类名固定），要求生成时**优先采用这些模式**。这样等于给了「绝美」的具象参照，而不是只靠文字规则。

2. **后续可选：引入 shadcn/ui 等组件库**  
   生成时要求「使用项目内的 Button/Card/Input 组件」，模型只负责组合与文案；视觉质量由组件库保证。需要先安装并配置组件库，再改生成 prompt 与运行环境（预览能解析这些组件）。

3. **多阶段生成（中长期）**  
   先出一版「布局+区块语义」，再单独一版「每块用哪种样式/组件」，降低单次生成的负担，提高一致性。

---

## 三、已实施：使用现成组件库

1. **预览用 UI 组件**（`src/components/preview-ui/`）  
   - 提供与 shadcn 风格一致的 **Button、Card（CardHeader/CardTitle/CardContent/CardFooter）、Input、Label**，纯 React + Tailwind，无 Radix 依赖。  
   - 预览时由 **LivePreview** 将这些组件注入为全局变量，生成代码中**无需 import**，直接写 `<Button>`、`<Card>` 等即可。

2. **生成 prompt**  
   - **UI_BUILDING_BLOCKS** 已改为「必须使用上述组件」：主按钮用 `<Button>`，卡片用 `<Card>`+`<CardHeader>` 等，表单项用 `<Label>`+`<Input>`；并明确约定**不要写组件 import**、不要用裸 `<button>`/`<div>` 手写样式。

3. **效果**  
   - 与「其他应用用组件库」一致：观感由现成组件保证，模型只负责组合与文案，生成 UI 的下限和一致性得到提升。
