# 新 UI 生成提示词评估报告

> 由「最强大脑」与「专家团队」对新版 UI 生成提示词（整合 200 家企业设计理念 + Role/Task/组件约束/平台布局）进行评估，指出问题与优化建议。

---

## 一、评估对象

- **新提示词结构**：Role → Task → Strict Component Constraints → Platform Layout Rules → Design & Code Guidelines → Design Philosophy（200 家）→ 样式与视口。
- **用户提示**：Context: Page Requirements + 动态注入的页面需求描述（getNodePageDescription 或 nodeLabel+requirement 兜底）+ 用户补充 + 设备与禁止留白。

---

## 二、最强大脑评估：问题与风险

### 2.1 结构问题

1. **Design Philosophy 位置靠后**  
   - 设计理念放在系统提示中段偏后，模型在长 prompt 下可能对后半段权重降低。  
   - **建议**：将「主内容区有实质」「禁止空白」等与输出强相关的 1–2 条提前到 Task 或 Strict Component Constraints 之后，形成「任务 → 组件约束 → 内容实质 → 平台与设计哲学」的顺序。

2. **Task 与 Design & Code Guidelines 重复**  
   - Task 已说「输出完整代码、禁止空白页」，Guidelines 又强调「完整 JSX、禁止骨架」。  
   - **建议**：Task 保留「输出完整、可见的 React 页面代码」；Guidelines 中仅保留代码格式与组件命名（App/Page），删除与 Task 完全重复的禁止空白表述，避免 token 浪费与指令冲突。

3. **组件名 App 与 Page 双选**  
   - 当前允许「App 或 Page」，LivePreview 已支持两者，但若模型随机二选一，与「必须命名为 App」的旧约束相比，可预期性略降。  
   - **建议**：若希望预览逻辑统一，可固定为「仅输出 \`export default function App() { ... }\`」；若希望与用户模板一致，保留双选并确保 LivePreview 对 Page 的解析稳定。

### 2.2 约束与可操作性

4. **「绝对禁止编造未在列表中的组件」**  
   - 表述清晰，但未明确「若用了未列出组件会怎样」（如运行时报错、预览空白）。  
   - **建议**：可补充一句「运行环境仅注入上述组件，使用其他名称会导致预览无法渲染」，增强遵守动机。

5. **Platform Layout Rules 与 viewportRule 重复**  
   - 平台规则已说明移动用 NavBar/BottomNav、PC 用 AppBar/Sidebar；文末又有「样式与视口」的 viewportRule（根容器 class）。  
   - **建议**：合并为一节「Platform & Viewport」，既写导航组件选择，也写根容器 class（max-w-7xl / w-full overflow-x-hidden），减少分散。

6. **Mock 数据「符合真实业务逻辑」**  
   - 要求合理，但未给出示例粒度（如订单号格式、金额单位、日期格式）。  
   - **建议**：在 Design & Code Guidelines 中加一句「Mock 数据示例：中文商品名、合理价格与数量、简短日期或状态文案」，降低模型编造过于离谱数据的概率。

### 2.3 与 200 家理念的融合

7. **Design Philosophy 为英文小节**  
   - 系统提示其余部分为中文，仅设计哲学为英文，风格不统一。  
   - **建议**：改为中文表述（如「设计理念（200 家头部企业共性）」），与 Role/Task 语言一致，便于模型统一理解。

8. **「主内容区有实质」在哲学中已出现**  
   - 该条与 Task/用户提示中的「禁止留白」重复，但放在哲学中有助于解释「为什么」要这样做。  
   - **建议**：保留哲学中的表述；在 Task 或用户提示末尾保留一句硬性约束「主内容区必须用组件填满并有真实文案」，形成「理念 + 硬约束」双重强化。

## 三、专家团队评估：优化建议汇总

### 3.1 高优先级（建议本迭代落实）

| 序号 | 问题 | 优化建议 |
|------|------|----------|
| 1 | Design Philosophy 位置偏后 | 将「主内容区有实质」「禁止空白」提前到 Task 后 1–2 条，或单独成段「Content Requirements」置于组件约束之后。 |
| 2 | 中英混用 | Design Philosophy 小节改为中文，与整体提示词语言一致。 |
| 3 | 平台与视口分散 | 合并 Platform Layout Rules 与末尾「样式与视口」为「Platform & Viewport」一节，导航组件 + 根容器 class 一起写。 |
| 4 | 未列出组件的后果未说明 | 在 Strict Component Constraints 中补充：仅注入上述组件，使用其他名称会导致预览无法渲染。 |

### 3.2 中优先级（可选下一迭代）

| 序号 | 问题 | 优化建议 |
|------|------|----------|
| 5 | Task 与 Guidelines 重复 | 精简 Guidelines，去掉与 Task 完全重复的「禁止空白/骨架」表述，只保留代码格式与命名。 |
| 6 | Mock 数据粒度未引导 | 增加一句 Mock 示例引导：中文商品名、合理价格与数量、简短日期或状态。 |
| 7 | 组件名 App/Page 双选 | 若需与旧版一致，可固定为 App；若保留 Page，需在 LivePreview 与文档中明确支持。 |

### 3.3 低优先级（观察与迭代）

| 序号 | 问题 | 优化建议 |
|------|------|----------|
| 8 | pageDescription 为空时 | 当前兜底为 nodeLabel + requirement，已合理；可观察生成质量，若仍偏空可再强化「本页必须包含」的句式。 |
| 9 | 200 家条数较多 | 若后续发现 prompt 过长或模型对后半段执行不稳，可收缩为 3–5 条最核心（内容优先、主区有实质、克制用色、留白与层级、一致性）。 |

---

## 四、总结

- **新提示词优点**：结构清晰（Role/Task/组件/平台/设计/视口）、组件约束明确、200 家设计理念融入、页面需求可动态注入（getNodePageDescription），有利于生成一致且「有内容」的页面。
- **主要问题**：设计哲学位置偏后、中英混用、平台与视口分散、未列出组件的后果未点明；次要为 Task 与 Guidelines 重复、Mock 与组件名双选可再收紧。
- **建议执行顺序**：先做高优先级 1–4（哲学前置/中文化/合并平台与视口/组件后果说明），观察一版生成效果后再决定是否做中优先级 5–7。

以上为最强大脑与专家团队对新 UI 生成提示词的评估与优化建议。
