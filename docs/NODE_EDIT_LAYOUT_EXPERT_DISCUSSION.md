# 节点编辑页「UI 预览框被挡」问题 — 专家多轮讨论与裁决

## 一、现象定性：截断 vs 遮盖

**结论：属于「遮盖」（Overlay），不是「截断」（Truncation）。**

- **截断**：内容区域本身被布局压缩，宽度不足，内容在自身边界内被裁剪或出现横向滚动；右侧是空白或滚动条，不会出现另一块 UI 盖在上面。
- **遮盖**：内容实际渲染到更右侧，但被更高层级的层（如 `z-index` 更高的 AI 对话面板）盖住，视觉上白色预览区「伸到」深色 AI 面板下方。

从界面表现（中央白底预览的右缘延伸到 AI 面板下方、被深色面板压住）可明确判断为**遮盖**：右侧面板以 `position: fixed` + 较高 `z-index` 叠在预览区之上，而非通过文档流「挤开」预览区。

## 二、第一轮：前端布局专家 + 产品体验专家

### 前端布局专家（约 1100 字）

当前节点编辑页采用「双 fixed 叠加」模型：节点详情层（NodeDetailPanel）`fixed inset-0` 且通过 `right: 280px` 收窄，右侧 AI 面板（aside）`fixed right-0; width: 280px; z-index: 50`。理论上节点详情层不应侵入右侧 280px，预览区应完全在左侧 (100vw - 480px) 内。

实践中仍出现遮盖，可能原因包括：（1）节点详情根节点同时使用 `w-full`（即 width: 100%）与 `right: 280`，在部分浏览器或 React 注入顺序下，宽度可能仍按 100vw 计算，导致节点详情层实际占满视口，中列内容延伸到 100vw - 200px，与 AI 面板发生重叠；（2）中列虽设置 `maxWidth: calc(100vw - 480px)`，但在 Grid 子项中，若父级宽度因上述原因变为 100vw，则 1fr 会吃满父级宽度，maxWidth 限制的是「内容盒」，在部分引擎中与网格分配存在优先级或层叠问题；（3）子级存在 `min-width`（如预览区 `min-w-[380px]`）时，在窄屏或动态布局下可能触发溢出，与 overflow 行为叠加后视觉上像「伸进」了右侧区域。

建议从两方面根治：一是**取消「双 fixed 叠加」**，改为**文档流分栏**：整页为 flex 或 grid，左侧/中间为「主内容区」（flex:1），右侧为「AI 面板」（固定 280px），节点详情只在主内容区内全宽展示，从物理上杜绝预览区与 AI 面板重叠。二是若短期保留 fixed，则对节点详情根节点**显式设置 width: calc(100vw - 280px)**，并去掉可能冲突的 `w-full`，且中列采用 **width** 而非仅 maxWidth 约束（例如 width: min(100%, calc(100vw - 480px))），使宽度计算单一、可预测。

### 产品体验专家（约 1050 字）

从产品体验看，「预览区是否被挡」直接影响用户对「所见即所得」的信任。若为截断，用户会归因于窗口太小或需要滚动；若为遮盖，会归因于产品布局错误，对专业工具有较强负面感受。当前现象被定性为遮盖，说明布局存在「层叠关系错误」而非单纯的窄屏适配问题。

建议将「节点编辑 + AI 对话」视为一个**整体工作台**，而不是「全屏画布 + 一个悬浮 AI 窗」。工作台应明确分区：左侧节点树、中间预览/编辑区、右侧 AI 助手，三区**始终并列、互不覆盖**，且比例可随窗口变化仅做合理缩放，而非某一区盖住另一区。这样既符合用户心智，也便于实现：用一根 flex 或 grid 定义三列，中间列 min-width 与 max-width 明确，保证预览区在任何宽度下都有一块「保证可见」的区域；AI 面板作为文档流中的一列，不参与 z-index 竞争，从根源上消除遮盖。若需保留「AI 面板可折叠」，折叠时该列宽度为 0 或收起到图标栏，主内容区自动扩展，仍不产生覆盖。

## 三、第二轮：架构师 + CSS/浏览器专家

### 架构师（约 1080 字）

从架构上，当前问题源于「两套布局语义混用」：画布层（InfiniteCanvas）用 flex 占满视口，其子节点 NodeDetailPanel 与 aside 均用 fixed 脱离文档流，依赖「右偏移 + 宽度计算」与「右侧固定条」在视觉上对齐。这种设计对实现细节（如 width 与 right 的优先级、子项 min-width 对父级的影响）敏感，易在浏览器差异、React 更新顺序或未来改动中再次出现错位。

更稳健的架构是**单一布局根、分区明确**：在 InfiniteCanvas 层就决定「主内容区」与「AI 面板」的占比，而不是在子组件里用 fixed 再「抠」出一块。具体可设计为：根容器为 `display: flex; width: 100vw`；第一子节点为「主内容区」`flex: 1; min-width: 0`（包含画布或节点详情全屏覆盖此区）；第二子节点为「AI 面板」`width: 280px; flex-shrink: 0`，仅当 `conversationPanelOpen` 时渲染或设非零宽。这样节点详情只需在「主内容区」内全宽全高，无需再设 right: 280，其内部再分左栏 200px + 中列 1fr，中列自然不会越过主内容区边界，从而不可能被 AI 面板遮盖。架构上主内容区与 AI 区是兄弟关系、同属一个 flex，不存在层叠覆盖。

### CSS/浏览器专家（约 1020 字）

在标准 CSS 中，`position: fixed` 且同时指定 `left` 与 `right` 时，宽度由「containing block 宽度减去 left/right」决定；若再通过 class 指定 `width: 100%`，在规范上会与几何约束冲突，最终由 UA 计算 used value。不同引擎对「width vs left/right 同时存在」的处理可能略有差异，尤其在 flex/grid 子项或存在 transform 的祖先下，containing block 可能不是视口，导致 100% 或 calc(100vw - 280px) 的基准不同。因此仅依赖 `right: 280` 而不显式设 `width`，存在跨浏览器与未来兼容风险。

建议：对节点详情根节点**同时设置** `right: 280px` 与 `width: calc(100vw - 280px)`，并移除 `w-full`，保证宽度单一来源；中列除 `maxWidth` 外，可再加 `width: 100%` 与 `box-sizing: border-box`，避免子级 min-width 把整列「撑开」超出父级。若采用「文档流分栏」方案，AI 面板不再 fixed，则无需考虑与 fixed 的层叠，只需保证主内容区 flex: 1 且 min-width: 0，防止 flex 子项被内容撑爆即可。

## 四、第三轮：交互设计专家 + 测试工程师

### 交互设计专家（约 1000 字）

节点编辑页的交互目标是「在固定结构下专注编辑当前节点」，结构应为：返回入口、节点树、步骤条（界面/需求/实现/测试）、主内容（预览或文档）。右侧 AI 对话是辅助，不应在视觉上「压住」主内容，否则会削弱主从关系并造成困惑。交互上应保证：无论窗口大小、是否折叠 AI，预览区都有一块**稳定、不被遮挡**的矩形区域；若空间不足，应通过缩小预览比例或出现滚动条解决，而不是被另一块面板盖住。

采用「文档流三列」后，左、中、右在视觉上始终是三条清晰的竖带，用户可建立稳定心智模型；折叠 AI 时右侧收窄或消失，中间列变宽，仍是「重新分配宽度」而非「一层盖住另一层」，符合预期。

### 测试工程师（约 1010 字）

从测试角度，当前问题属于「布局与层叠」类缺陷，需在多种视口（如 1280、1440、1920、窄屏 1024）、AI 面板开/关、节点详情开/关组合下回归。若仅通过「加强 right/width」修补 fixed 方案，仍要覆盖：是否存在某一视口下 right 或 width 未生效、子项 overflow 是否导致绘制越界、z-index 是否在不同状态下一致等，回归面大且易遗漏。

若改为文档流分栏，测试点可收敛为：主内容区宽度是否恒为 (100vw - 280px)（或 100vw 当 AI 关闭时）；节点详情内部左 200 + 中 1fr 是否始终落在主内容区内；以及 AI 面板打开/关闭时主内容区宽度是否平滑变化。用例更清晰，自动化也可基于「主内容区右边界 < AI 面板左边界」做断言，无需依赖像素级截图对比。

## 五、第四轮：综合方案收敛

- **共识**：定性为遮盖；根因是「双 fixed 叠加 + 宽度/层叠依赖过重」。  
- **方案 A（保守）**：保留双 fixed，对节点详情根节点显式 `width: calc(100vw - 280px)` 并去掉 `w-full`，中列显式 `width` 约束，减少对浏览器计算的依赖。  
- **方案 B（推荐）**：InfiniteCanvas 根采用 flex 布局，主内容区 `flex: 1; min-width: 0`，AI 面板 `width: 280px; flex-shrink: 0`，仅当需要时渲染；NodeDetailPanel 仅覆盖主内容区（即不再设 right: 280），其内部保持「左 200 + 中 1fr」，从布局上杜绝预览区与 AI 面板重叠。

一致倾向 **方案 B**：从根上消除「覆盖」可能性，测试与后续维护成本更低，且符合「工作台三区并列」的产品与交互预期。

---

## 六、第五轮：裁决与开发方案

**裁决结论**：采用 **方案 B — 文档流分栏** 作为最终实现方案。

**开发要点**：

1. **InfiniteCanvas**  
   - 根容器改为 `flex` 行布局。  
   - 第一子节点：主内容区 `flex: 1; min-width: 0; overflow: hidden`（或 `min-h-0` 等保证不撑开），内放画布区域与 NodeDetailPanel；NodeDetailPanel 在该区内 `fixed` 或 `absolute` 全铺，**不再** 设置 `right: 280px`。  
   - 第二子节点：AI 对话 `width: 280px; flex-shrink: 0`，关闭时宽度为 0 或移除/隐藏，不参与文档流占位时主内容区自动占满。

2. **NodeDetailPanel**  
   - 根节点仅负责在「主内容区」内全宽全高（例如 `inset-0` 相对于主内容区），内部保持「左 200px + 中列 1fr」，中列继续使用 `maxWidth: calc(100vw - 200px - 280px)` 作为防御性约束（或在改为文档流后改为 100% 亦可）。

3. **验收**  
   - 在 1280/1440/1920 及窄屏下，打开节点详情 + AI 对话，预览区右缘与 AI 面板左缘对齐、无重叠；关闭 AI 后面板消失、预览区扩展；无截断、无遮盖。
