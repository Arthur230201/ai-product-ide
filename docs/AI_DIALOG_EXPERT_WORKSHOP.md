# AI 对话框：最强大脑与专家团队研讨纪要

> 研讨形式：5 轮（发散 3 轮 → 收敛 2 轮），最后由乔布斯执行审计并给出结论。  
> 背景：当前已实现底部 CommandBar 对话区 + 右侧 Stitch 风格对话窗口 + 澄清请求与回复闭环。

---

## 第一轮（发散）：问题与机会

**产品经理**  
- 当前对话是「单轮展示」：每条 AI 回复是前端摘要，不是模型真实输出。用户会以为「AI 就说了这一句」，若后端将来返回长文说明，没有展示渠道。  
- 澄清只在建图流程里触发，编辑节点（生成 UI、分析代码）没有澄清能力；需求不清时只能失败或猜。

**UX 研究员**  
- 两处入口（底部条 + 对话窗口）展示同一份对话，但「在对话窗口中查看」容易被忽略，澄清时自动弹窗又可能打断专注。需要统一心智：什么时候用条、什么时候用窗。  
- 空状态「在这里会显示你的输入与 AI 的回复」没有引导下一步（例如「试试描述你的产品想法」），新用户可能不知道能做什么。

**前端架构**  
- 对话状态在 store，CommandBar 与 ConversationPanel 共享；澄清回复通过 `pendingClarificationReply` + useEffect 触发二次请求，链路长、可读性一般，后续若加「取消澄清」「编辑上一条」会更难维护。  
- 消息只有内存态，刷新即丢；若要做「继续上次对话」或排查问题，没有留痕。

**设计负责人**  
- 底部条内对话区 max-h 280px，在 13 寸屏上会吃掉不少画布；小屏更吃紧。可以考虑默认折叠，仅保留「最近 1 条用户 + 1 条 AI」或只显示「打开对话窗口」入口。  
- 澄清选项是文字按钮，信息密度高；可做成卡片（标题 + 一句描述 + 示例），更易扫读。

## 第二轮（发散）：延伸与风险

**产品经理**  
- 若把「对话」当成一等公民，可延伸：按会话保存/加载、导出对话为 PRD 附录、从某条消息「分支」重试（同一输入换模型或参数）。这些都会推高复杂度和排期。  
- 澄清的「选项」目前是建图场景的 3～4 个业务场景；若扩展到 UI 风格、技术栈、合规要求，选项会爆炸，需要从「固定选项」走向「结构化追问 + 自由补充」。

**UX 研究员**  
- 风险：用户习惯在底部条输入，澄清时被引导到右侧窗口，可能找不到输入框（底部条没有提示「请到右侧窗口回复」）或误在底部条再发一条，形成两条分支。  
- 机会：把「当前是否在等澄清」在底部条做轻量提示（如一条横幅：「AI 在等你补充说明 → 在右侧窗口选择或输入」），减少割裂感。

**前端架构**  
- 若后续支持多轮对话上下文（把历史消息发给模型），需要区分「展示用消息」和「发给后端的消息」（可能截断、摘要、去附件），数据模型要提前想清楚。  
- 澄清回复的 useEffect 依赖 `pendingClarificationReply` 等，若用户快速连点两个选项，可能触发两次请求；需要防抖或「澄清中」锁。

**设计负责人**  
- 对话窗口和底部条视觉风格一致（深色、青色点缀），但窗口是「浮层」，和画布、节点详情是两层界面；若未来做「画布内气泡对话」（在节点旁弹出小窗），交互范式会再变，建议先定一个主范式再扩展。  
- 风险：功能越多，新用户学习成本越高；需要 onboarding 或首次使用时的单步提示（只做一次）。

## 第三轮（发散）：替代方案与边界

**产品经理**  
- 替代 A：不做独立对话窗口，只做底部条内对话区 + 澄清时在条内展开「选项卡片」和输入，一切在一处完成。优点：心智简单；缺点：条内空间有限，选项多时挤。  
- 替代 B：对话窗口作为主入口，底部条只保留「快捷输入 + 发送」，历史与澄清全部在窗口。优点：对话为一等公民；缺点：画布与对话割裂，需要频繁切焦点。  
- 边界建议：明确「对话」的职责——是「输入 + 结果反馈 + 澄清」的通道，而不是通用聊天；与画布/节点的操作（选中、拖拽、删节点）不通过对话完成。

**UX 研究员**  
- 可探索「情景化入口」：在画布空白处点击时，在点击位置附近出现小输入泡（类似 Notion 的 /），输入后发送到同一套对话流；这样既保留底部条，又减少「一定要去底部」的路径。  
- 边界：对话不替代项目画像、不替代节点详情的 spec/impl/test 编辑；只负责「和 AI 的一来一往」与澄清。

**前端架构**  
- 替代：澄清回复不走 useEffect，改为「澄清回复」专用 action（如 `submitClarificationReply(reply)`），由 ConversationPanel 或 CommandBar 直接调用，入参从 store 读 context；这样依赖更显式，便于测试和取消。  
- 边界：对话消息不做持久化（不写后端、不写 localStorage）是当前合理选择；若以后要做，再引入「会话 id」与后端同步。

**设计负责人**  
- 替代：对话窗口可设为「可停靠」——用户可把窗口拖成与画布左右分栏（类似 IDE 终端），而不是只能浮层或关闭。  
- 边界：不追求与 ChatGPT 等通用聊天产品功能对齐（无多模型切换、无分支、无分享链接）；保持「为产品/画布服务」的垂直定位。

## 第四轮（收敛）：共识与优先级

**共识**  
1. **双入口保留，但主次分明**：底部条是主入口（输入 + 紧凑对话区）；对话窗口是「展开视图」与澄清时的主战场，自动打开时配合轻量提示（如底部条横幅）减少迷失。  
2. **澄清能力逐步扩展**：先稳住建图澄清的体验与稳定性（防双请求、提示清晰）；再考虑在「编辑节点 / 生成 UI」流程中引入类似澄清（需求不清时先追问再生成）。  
3. **对话内容以「展示 + 澄清」为主**：不承诺首版就做多轮上下文发给模型、会话持久化或导出；优先让「用户看到自己说了什么、AI 回了什么、能回复澄清」闭环可靠。  
4. **技术债务控制**：澄清回复链路可重构为显式 action（如 `submitClarificationReply`），避免依赖 useEffect + 多个 store 字段的隐式联动；消息列表保留最近 N 条即可，不持久化。

**优先级（收敛后）**  
- P0（必须）：澄清回复防双请求；底部条在「等待澄清」时给出明确提示（如横幅或禁用输入并说明「请在右侧窗口回复」）。  
- P1（应有）：对话窗口空状态与首次打开的轻量引导；澄清选项的展示优化（如卡片化、描述可读）。  
- P2（可选）：编辑节点时的澄清；对话消息持久化或导出；画布内情景化输入泡。

## 第五轮（收敛）：落地方向与不做什么

**落地方向**  
1. **体验闭环**：用户从底部条输入 → 收到澄清时自动打开对话窗口并看到选项 → 在窗口选择或输入并发送 → 后端用「初始 + 澄清」再次建图 → 结果回写画布并更新对话区；全程无断点、无歧义入口。  
2. **文案与引导**：统一「AI 在等你补充说明」的呈现（底部条 + 窗口内），并考虑在对话窗口空状态加一句行动建议（如「在下方输入产品想法，或上传文件」）。  
3. **代码质量**：将「澄清回复」从「设置 reply + 依赖 useEffect」改为显式调用（例如 CommandBar 或 Panel 调用 `submitClarificationReply(reply)`，内部读 context 并调 `executeCreate`），便于单测与取消逻辑。

**明确不做什么（本阶段）**  
- 不做多轮对话上下文发给模型（保持单轮/澄清扩展单轮）。  
- 不做会话持久化、导出、分支、分享。  
- 不做「画布内气泡对话」或可停靠窗口（保留当前滑出浮层）。  
- 不做与通用聊天产品看齐的复杂功能（多模型、长对话管理）。

## 乔布斯审计：最终结论

**审计人视角（乔布斯）**  
产品里最怕两件事：**功能堆砌**和**一半体验**。  
当前 AI 对话框已经做了两件事：**在底部条展示对话** + **用独立窗口做澄清**。方向对——用户能看见自己说了什么、AI 回了什么，并且有地方回答追问。但若「澄清」和「主输入」割裂（用户不知道要去窗口回复），或澄清回复触发两次请求，那就是**一半体验**：做了一半，没做透。

**结论（一句话）**  
**把「澄清」这一条路走透，再谈扩展。**  

- **做透**意味着：  
  - 用户不会搞错「在哪里回复」——要么底部条在等澄清时有不可忽视的提示并引导到窗口，要么澄清时底部条输入暂时禁用并文案说明。  
  - 技术上不会因为连点或重复提交而触发多次建图请求。  
  - 对话窗口的澄清选项一目了然（当前若选项过长、过密，就收一收或卡片化），用户点一下就知道自己在选什么。  

- **再谈扩展**意味着：  
  - 不在此阶段加「多轮上下文」「会话保存」「编辑节点澄清」等新能力；先把建图澄清的体验与实现打磨到「无槽点」。  
  - 产品文档（如 AI_DIALOG_CONVERSATION_DESIGN.md）可补充一句原则：**对话为画布与生成服务，不为聊天而聊天**；任何新功能先问：是否让「从想法到画布/节点」更顺，而不是让对话本身更花哨。

**最终裁决**  
- **保留**：底部条对话区 + 右侧对话窗口 + 建图澄清闭环。  
- **必须修**：澄清回复防双请求；「等待澄清」时的明确引导（底部条提示或输入禁用 + 文案）。  
- **优先优化**：对话窗口空状态与澄清选项的可读性（引导文案、选项展示）。  
- **暂停**：多轮上下文、会话持久化、编辑节点澄清、可停靠/画布内对话等，列为后续迭代，不进入当前冲刺。
