# 从系统目的出发：优化方向与 UI 质量 —— 三轮讨论纪要

> 最强大脑联合专家团队，针对「意图/领域过拟合」「页面数应由 LLM 定义」「UI 输出难看」的反思与方案。
>
> **原则**：只在一开始做好限制（prompt + 组件库 + 推荐写法），不做事后补救（不做生成后校验、未达标提示或重试），保持系统简洁不冗余。

---

## 前提：用户的批评（共识）

1. **定义无标准、不准确**：此前对「管理系统 5–8 页」「电商 5+ 页」等节点数量限制，无数据来源，仅为经验性约定。
2. **页面节点数量应交由 LLM 定义**：系统不应硬编码「必须几页」，而应由模型根据用户意图与业务完整性自行推断。
3. **硬编码限制导致过拟合**：只对少数常见场景（管理、电商）做特殊处理，泛化性差；当用户需求是长尾、新颖、市面上少见的系统时，反而被错误约束。
4. **系统真正价值**：**只有当市面上缺少类似系统时，用户才需要我们**。我们的能力应体现在「泛化、多样、新颖」，而非「再做一个常见后台/电商模板」。
5. **UI 输出难看**：需要从根因出发，给出可执行的解决方向。

---

## 第一轮讨论：系统目的与优化方向

**参与视角**：产品负责人、系统架构师、领域建模专家。

### 1.1 我们为谁服务？何时被需要？

- **目标用户**：需要从想法/文档/草图快速得到「可运行的产品形态」的人；往往是在做**市面上少见或不存在**的产品形态（新领域、新流程、垂直场景、内部工具等）。
- **被需要的时机**：恰恰是**没有现成模板、没有成熟竞品**的时候。若只是「再做一套管理系统/电商」，用户大可直接用模板或成熟 SaaS。
- **推论**：产品的差异化在于**长尾需求、新颖组合、未知领域**的覆盖能力，而不是对「管理系统」「电商」等少数类型的精致优化。

### 1.2 优化方向应是什么？

- **优先方向**：**泛化能力** —— 让 LLM 充分理解用户意图，自行推断业务边界、页面数量、页面类型与结构；系统只提供「清晰输入、一致约束、可复用设计语言」，不替模型做业务决策。
- **应避免**：对少数行业/类型做**硬编码规则**（如「管理系统必须 5–8 页」「电商必须 5+ 页」），导致：
  - 无数据支撑、无标准；
  - 长尾需求被错误裁剪或扭曲；
  - 模型能力未被充分利用，反而被规则限制。

### 1.3 第一轮结论

| 维度 | 结论 |
|------|------|
| 系统目的 | 服务「市面上缺少类似系统」的场景，差异化在泛化与长尾。 |
| 优化方向 | 泛化优先：清晰意图输入 + 设计系统约束 + 交给 LLM 推断 scope/页面数/结构。 |
| 不应做 | 按行业硬编码页面数量、固定典型页面列表、用规则替代 LLM 的推断。 |

## 第二轮讨论：泛化 vs 特殊处理

**参与视角**：架构师、领域建模、Prompt 工程师。

### 2.1 当前「领域模块 + Scope Rule」的问题

- **生图**：Scope Rule 中写死「管理系统 5–8 页」「电商 5+ 页」「任务 3–4 页」；意图加工层又通过 `scopeRuleCreate` 对用户输入追加「请输出 5–8 个典型页面…」。  
  → 页面数量与类型被**系统**决定，而非由**用户意图 + 模型推断**决定；对非管理、非电商的描述既不适用，也容易误导。
- **生成 UI**：按领域注入「管理后台必须侧栏+顶栏」等片段。  
  → 对明确是管理后台的页面可能有帮助，但对「像管理但更轻」「混合型」或未知类型会过拟合，且与「交给 LLM 定义」的原则冲突。

### 2.2 页面/节点数量应由谁定义？

- **结论**：**由 LLM 定义**。  
  - 输入：用户原始描述（可经意图加工做**语义澄清、上下文补全**，但不注入「必须几页」「必须包含哪些页」）。  
  - 输出：模型根据对业务的理解，推断需要多少节点、每个节点是什么、如何连接；可能 3 页、可能 8 页、可能 12 页，取决于业务完整性而非我们写的数字。
- **意图加工层应做**：  
  - 澄清歧义（如简略描述展开为完整句子）；  
  - 补全上下文（如当前节点名、本页在整体中的角色）；  
  - **不**追加「请输出 N 个页面」「必须包含 A、B、C 页」等约束。

### 2.3 第二轮结论

| 维度 | 结论 |
|------|------|
| 页面数/节点结构 | 完全交给 LLM 根据用户意图与业务完整性推断；移除所有硬编码的「N 页」「典型页面列表」约束。 |
| Scope Rule | 改为「根据用户描述推断业务边界与页面集合，保证每个节点有足够 description/userStories」，删除按类型规定具体数字与固定列表。 |
| 领域模块 | 不再提供「scopeRuleCreate」式的页数/典型页枚举；可保留轻量「语义提示」（如「用户可能在描述管理类需求」）供模型参考，不强制；UI 侧的布局建议改为可选、弱约束或移除。 |

## 第三轮讨论：UI 输出难看怎么解决

**参与视角**：设计负责人、前端架构、UX 专家、交付质量。

### 3.1 根因归纳（与 WHY_OTHER_APPS、STITCH_PLAN 对齐）

- **组件使用不彻底**：虽已要求使用 Button/Card/Input 等现成组件，但生成结果仍常见裸 `div`+Tailwind 堆砌、或组件与手写样式混用，导致观感不统一、像「模型在发明样式」。
- **单次生成负担过重**：布局+样式+内容+交互一次完成，模型容易顾此失彼；缺少「先结构后样式」或「先参照后生成」的拆解。
- **缺具象参照**：主要靠文字规则（Constitution、Premium Brief）；缺少 1–2 个**可直接模仿的代码片段**（如「主按钮长这样」「卡片长这样」），模型容易自由发挥成泛化 AI 感。
- **规则冗长、优先级不清**：系统 prompt 很长，颜色/字体/布局/禁止项混在一起，模型可能抓不住重点，导致「写了但没做到」。

### 3.2 解决方向（不依赖领域过拟合）

1. **强化「必须用现成组件」的约束与校验**  
   - 在 prompt 中更突出：**禁止**手写裸 button/div 做主要 UI；列表、表单、导航必须用 Building Blocks 中的组件。  
   - 可选：生成后做轻量 AST/正则检查（是否出现 Button/Card/Input 等），未使用则重试或提示「请使用提供的组件库」。

2. **设计系统前置 + 少量具象示例**  
   - 保持 UI Constitution + Premium Brief 作为默认风格；在此基础上增加 **2–3 段可直接模仿的 TSX 片段**（主按钮、卡片、输入框+标签），明确写「优先采用下列写法」。  
   - 这样等于给「好看」一个具体参照，而不是只靠文字描述。

3. **多阶段/先结构后样式（与 Stitch 对齐）**  
   - 有条件时：先出一版「布局+区块语义」（section、header、main、卡片区、表单区），再单独一版「每块用哪种组件/样式」。  
   - 降低单次生成的认知负担，提高一致性；不依赖「管理后台/电商」等类型特例。

4. **不通过领域特例解决观感**  
   - 不依赖「管理后台必须侧栏+顶栏」等按类型注入来提升观感；**观感应由统一的设计系统 + 组件库 + 示例片段保证**，这样对长尾、新颖类型同样有效。

### 3.3 第三轮结论

| 维度 | 结论 |
|------|------|
| UI 难看根因 | 组件使用不彻底、单次生成负担大、缺具象参照、规则多而重点不突出。 |
| 方案优先级 | ① 生成前强化组件强制（只用提供的组件，禁止裸 div/button）；② 设计系统前置 + 2–3 个可模仿代码片段（生成前注入）；③ 多阶段（先布局后样式）可选；④ 不靠领域特例、不做事后校验。 |

## 综合方案与可执行项

### A. 意图与生图：去除过拟合，交给 LLM 定义

| 项 | 动作 |
|----|------|
| 1 | **generate-graph 的 Scope Rule**：删除「管理系统 5–8 页」「电商 5+ 页」「任务 3–4 页」等具体数字与固定页面列表；改为「根据用户描述推断业务边界与完整页面集合，页面数量与类型由业务需求决定；为每个节点填写足够的 description 与 userStories」。 |
| 2 | **意图加工 create 模式**：不再根据领域追加「请输出 5–8 个典型页面…」；仅做可选语义澄清（如将极简描述扩展为完整句），不注入页数或典型页列表。 |
| 3 | **领域模块**：移除或清空 `scopeRuleCreate`（不再规定页数/典型页）；`typicalPages` 仅作 fallback 图的可选参考，不写入给 LLM 的 prompt；`forUISystemPrompt` 中与「必须侧栏+顶栏」等强约束可移除或改为极弱提示，避免按类型过拟合。 |

### B. 生成 UI：只做事前约束，不做事后补救

| 项 | 动作 |
|----|------|
| 4 | **生成前组件强制**：在 system 中明确「生成前必须：只使用提供的 Button、Card、Input、StatCard、ListItem、EmptyState、PageHeader 等组件；禁止用裸 div/button 实现主要 UI」。不在生成后做「未达标」提示或重试，仅通过生成前约束保证输出。 |
| 5 | **生成前具象示例**：在 prompt 中增加 2–3 段「推荐写法」TSX 片段（主按钮、卡片、表单项），明确「输出必须优先采用下列代码模式」，让模型在生成前就有可模仿的参照。 |
| 6 | **生成 UI 的意图层**：不再按领域注入 `systemPromptSuffix`；观感由统一组件库 + 推荐写法保证。 |

### C. 文档与后续

| 项 | 动作 |
|----|------|
| 7 | **INTENT_AND_SYSTEM_PROMPT_DESIGN.md**：更新为「意图加工只做语义澄清与上下文补全，不规定 scope/页数；页面数量与结构由 LLM 推断」。 |
| 8 | **原则**：只在一开始做好限制（prompt + 组件库 + 推荐写法），不做生成后校验、未达标提示或重试，保持系统简洁不冗余。后续可考虑多阶段生成（先布局后样式），仍不新增事后校验。 |
| 9 | **高质量 UI**：用**通用定义**约束（主内容区与页面目标一致、禁止空白/占位、信息层级与操作入口清晰），**禁止**基于「管理」「商品」「列表」等特定词汇做分支或强制，保证泛化性。 |

## 总结表

| 议题 | 结论 |
|------|------|
| 系统目的 | 服务「市面上缺少类似系统」的场景；差异化在泛化与长尾。 |
| 优化方向 | 泛化优先：清晰输入 + 设计系统 + 交给 LLM 推断 scope/页数/结构。 |
| 页面数/节点 | 由 LLM 定义；移除所有硬编码页数与固定典型页列表。 |
| 意图加工 | 只做语义澄清与上下文补全；不追加页数或典型页约束。 |
| UI 难看 | 根因：组件使用不彻底、单次负担大、缺具象参照；方案：强化组件强制+示例片段+多阶段，不靠领域特例。 |

以上为三轮讨论结论与可执行方案，后续实现按 A/B/C 顺序落地，并持续以「泛化能力与默认观感」为衡量标准。
