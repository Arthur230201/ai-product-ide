# 意图加工与系统提示词体系设计

> **重要更新**：页面数量与节点结构**由 LLM 根据用户意图自行推断**，不做按行业/类型的硬编码规定（如「管理系统 5–8 页」）。意图加工只做语义澄清与上下文补全，不规定 scope。详见 `docs/SYSTEM_PURPOSE_AND_OPTIMIZATION_DISCUSSION.md`。

## 一、目标与原则

### 1.1 目标

- **用户输入 → 意图加工 → 再传给大模型**：在创建模式（生图）与生成 UI 模式下，对用户原始输入做**语义澄清与上下文补全**，产出更清晰的 prompt，再与系统提示词一起传给 LLM；**不**规定页面数量或典型页列表。
- **系统提示词是核心能力**：所有内置说明（生图架构师、UI Constitution、绝美风格、Building Blocks 等）统一作为**系统提示词**使用，熟练运用、版本化管理。
- **泛化优先**：系统价值在于服务「市面上缺少类似系统」的长尾场景；不对少数行业做固定页数/典型页的过拟合约束。

### 1.2 顶层原则（来自全网最佳实践）

- **系统提示词六层结构**（身份 → 主目标 → 指令优先级 → 行为规则 → 安全/不可变 → 输出约束）优先保证主目标与冲突时的优先级。
- **领域专用 = 提示词工程先行**：先通过 prompt 注入领域术语、工作流、约束与范围，再考虑 RAG/微调；快速迭代用 prompt，稳定后可按需加 RAG。
- **意图加工与系统分离**：加工层只产出「增强后的用户侧内容」和「可选系统片段」；与现有 system prompt 拼接，不替换既有设计。
- **行业专家思维固化**：把「最顶尖的人 / 各行业专家」的思考方式与技能固化为 skills 或可复用提示词模块，供意图加工时按检测到的行业/类型选用。

---

## 二、最强大脑与行业专家如何思考

### 2.1 最强大脑（系统级思考）

- **先定义问题再解**：创建模式下「定义有几个图节点、每个节点上有什么内容」是明确目标；生成 UI 模式下「本页在整体中的角色 + 用户故事 + 约束」是目标。
- **范围优先**：管理系统 5–8 页、电商 5+ 页、工具类 3–4 页等，由**类型**决定范围，不由一句短描述决定。
- **结构化优于自然语言**：意图加工输出可含「建议页面数、典型页面类型、关键实体、用户故事模板」等，便于下游 prompt 稳定。
- **可测试、可版本化**：系统提示词与领域片段像代码一样版本化、可 A/B、可回滚。

### 2.2 行业专家（领域技能）

| 领域       | 典型思考方式与技能 |
|------------|--------------------|
| 管理后台   | 角色/权限、仪表盘、CRUD、操作日志、系统设置；侧栏+顶栏+内容区；5–8 个典型页面。 |
| 电商       | 商品、订单、购物车、支付、促销、库存；列表/详情/流程闭环；5+ 页。 |
| 教育       | 课程、学习路径、作业/考试、进度、证书；师生角色与权限。 |
| 医疗       | 患者/病历、预约、处方、合规与隐私；严谨用语、数据安全表述。 |
| 政务       | 办事流程、申报、审批、公示、证照；多角色与状态机。 |
| 内容/媒体  | 创作、审核、发布、推荐、评论；多状态与工作流。 |
| 金融/风控  | 账户、交易、风控规则、报表；合规与审计表述。 |

这些固化为 **domain prompt 模块**（见下文），用于：  
- 生图时：注入 Scope Rule、典型页面列表、建议节点数；  
- 生成 UI 时：注入该类型页面的布局与组件约定（如管理后台必须 Sidebar+AppBar）。

## 三、架构：意图加工层 + 系统提示词库

### 3.1 整体流程

```
用户输入 (raw)
    ↓
意图加工 (intent-processor)
    ├─ 检测模式：create | generateUI
    ├─ 检测领域/类型：management | ecommerce | education | ...
    ├─ 选择/混合领域模块 (domains/*)
    └─ 输出：
         - enrichedUserPrompt: string   // 加工后的用户侧内容
         - systemPromptSuffix?: string  // 可选，追加到现有 system 后
         - detectedDomain?: string     // 供日志与后续扩展
    ↓
现有 system prompt + systemPromptSuffix
    +
enrichedUserPrompt
    ↓
LLM (callText / 生图 or 生成 UI)
```

### 3.2 创建模式（生图）

- **输入**：用户一句话（如「做一个管理系统」「电商订单后台」）。
- **加工**：**仅做语义澄清与上下文补全**；**不**按领域追加「5–8 页」「典型页面枚举」等。页面数量与节点结构由 **LLM 根据用户意图与业务完整性自行推断**。
- **输出**：`enrichedUserPrompt` 即为用户原始输入（或经简短澄清后的句子），直接作为传给生图 LLM 的用户部分。

### 3.3 生成 UI 模式

- **输入**：用户输入 + 当前节点 label + 节点描述/用户故事（baseDesc）。
- **加工**：拼节点上下文（节点名、本页说明）与用户补充；**不**按领域注入布局/组件强约束（如「必须侧栏+顶栏」），避免过拟合。
- **输出**：`enrichedUserPrompt` 作为生成 UI 的 user 内容；`systemPromptSuffix` 不再按领域注入，观感由统一设计系统与组件库保证。

### 3.4 领域模块设计（domains/*）

当前领域模块仅保留 **fallback 图** 等可选参考（如 `typicalPages`）；**不再**用于向 prompt 注入页数或典型页列表（`scopeRuleCreate` 已清空），也不再注入 UI 强约束（`forUISystemPrompt` 已清空）。扩展新行业时，不添加规定页数/固定列表的约束。

## 四、与现有实现的对接

- **生图**：`generate-graph.ts` 调用 `processIntentForCreate(userPrompt)`，用返回的 `enrichedUserPrompt` 作为用户部分；Scope Rule 已改为「由 LLM 根据用户描述推断页面数量与类型」，不再写死数字或固定列表。
- **生成 UI**：CommandBar 调用 `processIntentForGenerateUI(prompt, { nodeLabel, baseDesc })`，用返回的 `enrichedUserPrompt` 作为最终 user 内容；不再按领域传入 `systemPromptSuffix`。
- **系统提示词资产**：保持 `ui-constitution.ts`、`index.ts` 中的 CORE_*、MODE_*、UI Constitution、Building Blocks 等不变；观感由统一设计系统与组件库保证，不依赖领域特例。

---

## 五、如何扩展更多行业

1. **领域模块**：若仅作 fallback 或统计参考，可在 `domains/` 下新增模块并注册；**不要**在 `scopeRuleCreate` 或 `forUISystemPrompt` 中规定页数或布局强约束。
2. **可选：专家 skill**：将某领域的「思考方式」写成 `.cursor/skills/` 下的 SKILL.md，供人工或后续自动调用；不通过意图加工层向 LLM 注入固定页数或典型页列表。

## 六、参考资料与材料来源

- **System prompt 设计**：身份与主目标优先、指令层级、行为规则、输出约束（Field Guide to AI、Prompt Guardrails 等）。
- **领域专用 LLM**：Prompt engineering 先行，再 RAG、再微调；领域术语与工作流注入（Google Cloud 三阶段、Vertical AI 趋势）。
- **意图与 prompt 增强**：用户 prompt 与系统 prompt 分离；在调用 LLM 前做 prompt enrichment、意图分类与路由（Agent Gateway、Voiceflow、Rasa 等）。

以上设计用于指导「意图加工层」与「分行业/分系统类型系统提示词」的实现与迭代，并保持与现有生图、生成 UI 链路的兼容。
